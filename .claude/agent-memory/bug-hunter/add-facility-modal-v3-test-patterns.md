**Radix `PopoverContent` renders in a portal appended to `<body>`, not inside the Dialog's DOM subtree.** `SupervisorCombobox` (`src/components/dashboard/settings/SupervisorCombobox.tsx`) opens its roster list in a shadcn `Popover` from inside `AddFacilityModal`'s `Dialog`. A locator scoped to the dialog — e.g. `addFacilityDialog.getByRole('listbox', { name: 'Existing supervisors' })` — never matches, even though the list is visibly rendered and the screenshot on failure shows it correctly populated. `toBeVisible()` times out with "element(s) not found" because the query root (the dialog element) doesn't contain the portaled node at all, not because the data hasn't loaded. **Fix:** query from `page`, not the dialog locator, for anything rendered through a shadcn `Popover`/`Dialog`-in-`Dialog` combination. This cost a wasted round of bumping the timeout from 10s→20s before the real cause (portal scoping) was found — timeout bumps don't fix a locator that's searching the wrong subtree.

**createFacility's contract** (`src/app/actions/organization.ts`): `types: string[]` joined with `', '` into `Facility.type`; supervisor resolution is 3-way — existing org member with role `supervisor` → `organizationUserFacility.upsert` (assigned), member with any other role → `success: false` before the facility is created (no orphan), unknown email → `createInvites([...], { facilityId })` (best-effort, row written via `invite.createMany` before the email-send attempt, so the DB row exists regardless of SMTP outcome in this sandbox).

**Seat/billing note:** `createInvites`'s seat-limit check (`getSeatUsage`) resolves `staffMax: null` (unlimited, unenforced) whenever the org has no subscription row — true for all of `settings-page.spec.ts`'s raw-seeded orgs — so the facility-scoped supervisor invite path needs no billing/subscription seeding, unlike the `worker-billing-gate` precedent in [[qa-still-open-2026-07-19-regression-tests]] (that one gates *worker* invites specifically, a different code path).

**Test file:** `tests/e2e/settings-page.spec.ts`, describe block `Settings page — Add Facility (multi-facility v3)`. Added `seedOwnerWithSupervisor()`/`cleanupSupervisor()` helpers (owner + a second org member with `role='supervisor'`, active, no facility assignment — `getSupervisorOptions()` only needs the role+active flags, not a facility link). Locators: facility-type checkboxes via `getByRole('checkbox', { name: <label> })` (Radix `Checkbox.Root` renders `role="checkbox"`, wrapping `<label>` supplies the accessible name); the "Other (specify)" toggle is a `role="button"` until clicked, then becomes a checkbox with an explicit `aria-label`; dialog accessible name is `/add a new facility/i` (title changed from "Add Facility"). Unit coverage in `AddFacilityModal.test.tsx` and `organization.test.ts` (`createFacility`/`getSupervisorOptions` describe blocks) was already thorough pre-existing work — spot-checked, not weakened, no gaps added.
