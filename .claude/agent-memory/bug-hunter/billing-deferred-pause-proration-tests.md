Branch `feature/billing-upgrade-proration-and-deferred-pause` (5 product commits) shipped two policy changes: every tier upgrade now classifies `immediate_prorate` regardless of time remaining (`src/lib/billing-plan-change.ts`), and a pause is now DEFERRED — it records `Subscription.pauseStartsAt` at request time and only sets `pausedAt` when `runBillingPauseSweep` (`src/lib/billing-pause-sweep.ts`) materializes it at the period boundary. `hasActiveBilling()`/`getPauseState()` in `src/lib/billing.ts` must read only `pausedAt`, never `pauseStartsAt` — that's the whole mechanism, guarded by a ⛔ comment in the source and pinned by `src/lib/billing.test.ts` (new file, 21 tests — did not exist before despite `billing.ts` being the single access-gating choke point).

Full coverage landed across 5 commits, one file at a time (repeated mid-task API-error deaths made incremental commit-after-each-file mandatory): `src/lib/billing.test.ts` (invariant), `src/lib/billing-pause-sweep.test.ts` (new, 15 tests), plus extensions to `resume/route.test.ts` (+3, the pending-pause-cancellation branch had zero prior coverage), `checkout/route.test.ts` (+3, the paused-subscription 409 guard), and `src/app/api/webhooks/stripe/route.test.ts` (+2, pauseStartsAt-preservation regression). `pause/route.test.ts` and `billing-plan-change.test.ts` were already comprehensive pre-existing/rewritten-by-code-ninja — confirmed green, deliberately not touched to avoid padding with duplicate tests.

**Why:** two testing techniques here were explicitly confirmed by the user as the right call, worth repeating on similar branch-ordering / field-omission bugs elsewhere in this codebase:
1. **Dual-condition ordering-proof fixture.** To prove branch A is checked before branch B (not just that A works), build a fixture satisfying BOTH conditions simultaneously (here: `PENDING_PAUSE_SUB_WITH_SCHEDULE` — pending pause AND a `stripeScheduleId`) and assert branch B's side effects never fire. A fixture satisfying only A doesn't prove ordering.
2. **Absence-of-key over value-equality for a preserve-by-omission mechanism.** When product code protects a field by leaving it OUT of a Prisma `update`/`create` payload (here: `pauseStartsAt` is never in `handleSubscriptionUpsert`'s upsert data, so Prisma structurally can't touch it), assert `.not.toHaveProperty('pauseStartsAt')` on the actual call args — not that the value is unchanged. A value-equality assertion still passes if someone "fixes" it by adding `pauseStartsAt: existing?.pauseStartsAt` back in, which reintroduces the exact race the omission was preventing.

**How to apply:** reach for pattern 1 whenever a route/sweep has two guard branches that could plausibly fire on the same row (schedule conflicts, dual pause states, etc.) — build the fixture that satisfies both and assert on the loser's non-invocation. Reach for pattern 2 whenever reviewing or writing a Prisma upsert/update where a field is intentionally omitted from the payload as the safety mechanism — check the actual mock-call args object, not just the final "value" the mock would have produced.
