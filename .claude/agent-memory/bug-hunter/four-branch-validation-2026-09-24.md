On 2026-09-24, validated four unpushed branches (each in its own `.claude/worktrees/agent-*` worktree) for migrations, e2e and adversarial correctness. Two non-obvious environment traps and one reusable technique surfaced.

**A second live Claude Code session was working the SAME worktrees concurrently.** Detected via: a spec file I'd just written (`tests/e2e/archived-course-learner-actions.spec.ts`) got silently rewritten under me with a different (better) implementation; `docker-compose.e2e.yml`'s `lms-e2e-*` containers were torn down and re-created mid-session; `playwright.config.ts` and test files in OTHER worktrees I hadn't touched yet were also modified when I got to them; `docs/local/OPEN-ISSUES.md` already had BUG-24 through BUG-31-adjacent entries dated the same day for exactly the defects I was about to find. **Why:** `docker-compose.e2e.yml` uses fixed `container_name`s (`lms-e2e-db` etc.), so ANY two sessions running `e2e:up`/`e2e:local` anywhere in the repo — even in different worktrees, even validating different branches — collide globally, not per-worktree. **How to apply:** before trusting an e2e result in this repo, check `docker ps` / `ss -ltnp :3005` for churn across the run, not just at the start. If contention is suspected, build fully isolated infra: `docker run` your own named Postgres/Redis/MinIO on non-standard ports, a throwaway `PW_PORT` override at the top of `playwright.config.ts` (`const PORT = process.env.PW_PORT || '3005'`, then template it into `baseURL`/`webServer.url`/`webServer.command`/`webServer.env`), and `npx prisma migrate deploy` + `npx prisma db seed` against that DB (both are idempotent/additive, safe to layer on an existing DB). Revert the `playwright.config.ts` edit and remove your custom `.env.e2e.*` file afterward. Also watch for OOM: two heavy `next start` processes plus Postgres/Redis/MinIO containers on one box was enough to get one server SIGKILL'd mid-run (`Killed` in the log, preceded by an unrelated Next.js `InvariantError` about a missing client reference manifest) — that failure pattern (every subsequent test timing out on a basic `input[type="email"]` locator) is infra exhaustion, not a product regression; don't report it as one.

**`prisma migrate reset` is hard-blocked for AI agents (Prisma 7.10+), even against an obviously-disposable scratch DB.** It throws `Prisma Migrate detected that it was invoked by Claude Code` and refuses without `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` carrying the user's literal consent text — there is no way to satisfy this unattended. Don't try to word around it. Instead, for a "fresh" DB between branches, just re-run `migrate deploy` (applies only what's new relative to whatever's already tracked in `_prisma_migrations`) followed by `db seed` — `prisma/seed.ts` is written to be idempotent (fixed UUIDs, explicit `deleteMany()` of the stateful tables) specifically so this works without a reset.

**Technique: proving two branches' migrations apply together, without touching either worktree.** Neither `20260924103000_add_question_incorrect_option_explanations` (quiz branch) nor `20260924120000_backfill_enrollment_completed_at` (enrollment branch) had ever been applied to a real DB. To prove both apply cleanly together in filename order on one database: copy `prisma/` from one worktree into a scratch dir, `cp -r` the OTHER branch's one new migration folder into its `migrations/`, write a minimal standalone `prisma.config.ts` there (`schema: 'prisma/'`, `datasource.url: process.env.DATABASE_URL`), and `ln -s <a-worktree>/node_modules` into the scratch dir so `node_modules/.bin/prisma` is available without an `npm install`. Then `migrate deploy` / `migrate status` / `migrate diff --from-config-datasource --to-schema prisma/ --script` against a fresh scratch Postgres. `migrate diff`'s v7 syntax dropped `--from-url`; use `--from-config-datasource` (reads the datasource from `prisma.config.ts`) paired with `--to-schema <dir>`. This repo's two PRE-EXISTING, always-present drifts are the HNSW index (`DROP INDEX "manual_chunks_embedding_hnsw_idx"`) and the `facilities` id/updated_at defaults — a diff showing exactly those two and nothing else is a clean pass, not a failure.
