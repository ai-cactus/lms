Covers `src/lib/notifications/{catalog,recipients,emit,digest}.ts`, `src/app/actions/notification-settings.ts`, the `STAFF_ADDED`/`DOCUMENT_UPLOADED` wiring in `documents.ts`/`organization-code.ts`/`invite/accept/route.ts`, and the Help Center content module (`src/lib/help/articles.ts`).

**`vi.hoisted` gotcha, reconfirmed:** any mock fn referenced by BOTH a `vi.mock('./module', () => ({...}))` factory AND used later in the test body (e.g. to set `.mockResolvedValue`) must be declared inside the SAME `vi.hoisted(() => ({...}))` call as the other mocks — not as a separate top-level `const mockFoo = vi.fn()` above/below it. Vitest hoists all `vi.mock` calls above regular `const`s, so a factory referencing a not-yet-hoisted `const` throws `Cannot access '...' before initialization`. Hit this once in `digest.test.ts` (had `mockResolveRoleRecipients` as a bare `const` next to a `vi.hoisted` block for the other two mocks) — fix is one `vi.hoisted` returning all three.

**Testing `periodKeyFor`'s ISO week math: verify against external reference dates, not by re-deriving the same algorithm.** `digest.ts`'s `isoWeekKey` implements the Thursday-of-week ISO 8601 rule. Rather than reimplementing that logic in the test to "check itself," pin known calendar facts from the ISO 8601 standard: 2026-08-03 (a Monday) → `2026-W32`; 2024-12-31 (a Tuesday) → `2025-W01` (ISO year differs from calendar year); 2023-01-01 (a Sunday) → `2022-W52`. These are real regression traps for any date-math refactor — an off-by-one in the Thursday shift silently breaks exactly these boundary cases while passing on any mid-week/mid-year date.

**`resolveRoleRecipients`: exclusion is applied AFTER the role-coverage check, by design — the highest-value regression case.** An actor who is the *sole* holder of a target role, with `excludeUserIds` containing their own id, must yield zero recipients WITHOUT triggering the owner fallback (`usedFallback: false`, `missingRoles: []`) — the role IS covered, it's just that its one holder authored the event. Getting this backwards (checking exclusion before coverage) would silently escalate every self-authored single-holder event to the owner. Test this explicitly; it's the single most important case in that module.

**Digest per-recipient own-event exclusion is a filter over a *shared* pending-event pool, not a per-recipient query.** `digest.ts` resolves recipients once per distinct route (cached by `roles.join(',')|fallbackToOwner`) and then filters `event.actorUserId === recipient.userId` per (recipient, event) pair when bucketing. A recipient who authored EVERY pending event routed to them still causes the underlying `NotificationEvent` rows to be marked `dispatched` (the digest run still "processes" them) even though `sendEmail` is never called for that recipient — assert both halves (no email sent, but `updateMany` still ran) or you'll miss a regression that silently stops dispatching orphaned events.

**Digest-send e2e is infeasible in this sandbox for the same reason `REM-003` (reminders) is self-skipped.** `runNotificationDigest` only runs via cron (registered in `instrumentation.ts`, gated by `NOTIFICATION_DIGEST_ENABLED`) or the manual `POST /api/system/notifications/run` route, which requires `verifySystemAdminCookie()` — exercising it in Playwright needs `PLAYWRIGHT_SYSTEM_ADMIN_COOKIE`, unset here (see `tests/e2e/reminders.spec.ts`'s `REM-003`, which self-skips with `test.skip(!cookie, ...)`). Don't write a new e2e spec that assumes this route is reachable; cover the digest orchestration at the unit level (`digest.test.ts`) instead, exactly as the reminders sweep does.

**The `ROLE_FALLBACK_TRIGGERED` instant-email sub-flow (owner gets notified their HR/clinical-director seat is vacant) is unit-covered, not e2e-covered — a deliberate call, not an oversight.** It's technically reachable via UI (seed an HR-less org, accept a real invite or join-by-code as a new worker, check MailHog), but as of 2026-08-03 the app's SMTP config points at real Zoho creds rather than the MailHog container (see [[signup-owner-only-e2e-env]] update), so nothing would actually land in MailHog to assert against right now — and the underlying routing/throttle logic already has thorough, fast unit coverage in `emit.test.ts` (`emitFallbackAlert`, 24h dedupe throttle, no-recursion guard). Re-litigating the same logic through a full HTTP+SMTP round trip would add flake risk for near-zero marginal coverage.

**`documents.ts`'s `emitNotificationEvent` call for `DOCUMENT_UPLOADED` (around line 264) is NOT wrapped in a local try/catch** — unlike the two other wiring call sites (`organization-code.ts`'s `joinOrganization`, `invite/accept/route.ts`'s `POST`), which both sit inside an outer try/catch that would at least catch a thrown error (even if that turns a successful upload/join into a user-facing error). `documents.ts` relies entirely on `emitNotificationEvent`'s own internal try/catch (verified never-throws in `emit.test.ts`) with zero defense-in-depth at the call site. Not a live bug — the callee's contract holds — but worth flagging in review if `emit.ts` is ever refactored in a way that could reintroduce a throw path.
