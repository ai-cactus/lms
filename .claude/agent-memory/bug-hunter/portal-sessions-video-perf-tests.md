Added coverage for PR 1 of the video-playback perf plan (branch `feat/video-course-speed`): `src/lib/auth/portal-sessions.ts` (new, zero prior tests, on every authenticated request path), plus abort/select changes in `video/[lessonId]/route.ts`, `courses/[id]/preview-video/route.ts`, and a from-scratch `courses/[id]/learn/route.ts` test file (that route had no test file at all before).

**jsdom `DOMException` is NOT `instanceof Error`, but Node's is.** `isAbortError()` in both video proxy routes checks `err instanceof Error && err.name === 'AbortError'`. These routes run server-side under real Node (verified via `node -e "new DOMException('x','AbortError') instanceof Error"` → `true`), so the check is correct in production. But vitest's `environment: 'jsdom'` (`vitest.config.mts`) overrides the global `DOMException` with jsdom's own implementation, which does NOT extend `Error` — so `new DOMException(...)` inside a test silently fails the route's `instanceof Error` check and the test asserts the wrong status (502 instead of 499) for reasons unrelated to the code under test. Fix: build the rejection as `Object.assign(new Error('...'), { name: 'AbortError' })` instead of `new DOMException(...)` when the assertion depends on `instanceof Error`. Contrast with `src/lib/upload/resumable-upload.ts`, which checks `instanceof DOMException` (not `Error`) — that code's existing tests correctly use real `DOMException` since jsdom's version still satisfies `instanceof DOMException`. Not a product bug — purely a test-environment artifact — do not report it as one.

**`getPortalSessions()` cookie-presence gating** (`src/lib/auth/portal-sessions.ts`): reads `cookies()` from `next/headers`, and only calls `adminAuth()`/`workerAuth()` (still imported from the same `@/auth` / `@/auth.worker` paths) for whichever portal's session cookie is present — checking both the plain and `__Secure-` prefixed names AND NextAuth's chunked variants (`<name>.0`, `.1`, …). On `cookies()` throwing (no request scope) it degrades to calling both, which is exactly why the **pre-existing** `route.test.ts` files for `video/[lessonId]` and `video-progress.ts` kept passing unmodified after this refactor — they mock `@/auth`/`@/auth.worker` directly and never mock `next/headers`, so `cookies()` throws in the jsdom test env and both auth calls fire like before. New tests targeting the cookie-presence behavior itself must mock `next/headers`'s `cookies()` to resolve with a fake jar (`{ getAll: () => [{name, value}] }`).

To prove `Promise.all` concurrency (not sequential `await`) in `getPortalSessions`, used deferred promises for both `adminAuth`/`workerAuth` mocks and asserted both were already invoked (via `vi.waitFor`) before releasing either — a sequential-await regression would leave the second mock uncalled at that point.

**`learn/route.ts` regression-lock pattern**: the route's `quizAttempts` include deliberately has no `take: 1` (client does `.find(a => a.timeTaken === null)` to locate an in-progress attempt, which is not always the newest completed row). Tested by asserting the mocked `enrollment.findFirst` call's `include.quizAttempts` object lacks a `take` key, AND by feeding a two-item quizAttempts array (completed attempt first, in-progress/`timeTaken: null` attempt second) and asserting both round-trip into the response. Also locked down that `latestAttempt` quiz-results building reuses `quizData.questions` from the course query rather than re-querying — done by registering a `prisma.quiz.findUnique` mock in the harness and asserting it's never called (would otherwise throw `undefined is not a function` if the mock weren't registered, catching an accidental re-add of that query even more bluntly).
