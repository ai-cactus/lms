**Full report:** `qa-reports/assign-surface-consolidation.md`. Verdict: PASS WITH RISKS, 20/21 criteria PASS, 1 BLOCKED (code-verified only). Tested on staging @ `e25f90b` (PR #606–#612), "QA B4 Multi-Facility Org LLC" fixture.

**CRITICAL — the "Duplicate" course row action was deliberately REMOVED (commit `b952373`, 2026-09-08, "not a desired product feature and caused two production incidents"), not merely broken.** `forkCourse`/`duplicateCourse` and their row-action entry are fully deleted from `src/`. Do NOT reach for Duplicate as a fixture technique in any future round on this codebase — it doesn't exist. This obsoletes the "Duplicate crashes with 500" finding in [[team-test-round-2026-09-04-pr584]] (was already-broken; is now gone entirely) and the "Duplicate finally confirmed working" claim in [[staging-claim-verification-2026-09-08]] (was true for one day, then the feature itself was retired).

**Consequence: there is currently no in-product way to create a fresh, never-assigned, assignable (non-`isGlobalCatalog`) course**, since (a) Duplicate is gone, (b) the wizard's mandatory Step 7 ("Assign & Publish") always writes a `CourseAssignment` before a course can be published — `isAssignSelectionValid` gates the Publish button itself — so a wizard-created course is NEVER assignment-less by the time you can navigate away from it. **The one reachable "genuinely never-assigned" state found this round: a true global-catalog course (`isGlobalCatalog: true`, e.g. "Personal Conduct Series 1" in the B4 org) that the org has never individually assigned yet.** Its row has an empty kebab menu in the list UI (no "Assign to staff" — `buildRowActions` returns `[]` for `isGlobalCatalog` rows), but the **standalone `/…/assign` page is still reachable by direct URL** (`assign/page.tsx`'s course query allows `isGlobal && published` regardless of list-UI affordance) and shows the true "never assigned" default state. Use this technique — navigate directly to `/dashboard/training/courses/<global-catalog-course-id>/assign` — any time a future round needs a genuinely fresh assignment-default fixture without creating new data.

**CONFIRMED FIX — the shared `CourseAssignment` no longer gets clobbered when a second surface adds one more person.** This was the whole point of the consolidation effort (8 surfaces writing one row through a sink that couldn't distinguish "clear" from "no opinion"). Live-proved: set an explicit deadline (with time)/reminder cadence/renewal cycle on a course via the standalone assign page, then added ONE more person via the **Staff Profile → Assign Course** modal (a structurally different code path, including its own separate "Set Completion Deadline" sub-dialog — left empty/untouched). Reopening the assign page showed deadline/cadence/renewal completely unchanged, and the newly-added person's own enrollment inherited the SAME shared deadline (not a fresh default) — strong double confirmation.

**CONFIRMED FIX — a deadline's time-of-day now survives a no-op re-save (`3012070`), AND the "past deadline" refusal (`PAST_DEADLINE_ASSIGN_MESSAGE = 'The deadline must be in the future.'`) correctly fires ONLY on a genuine change, never on re-submitting the same stored value.** `isPastDeadlineChange` in `src/lib/reminders/deadline.ts` compares `submittedTime !== stored?.getTime()` — an unchanged resubmit of an already-in-force (even now-imminent) deadline is explicitly exempt, by design ("re-submitting the deadline already in force is how a late joiner is added to an already-overdue course"). **Reusable technique for reaching a genuinely NEW past deadline through the UI despite the Due Date calendar's `minDate` (defaults to start-of-today, so no earlier DAY is selectable): pick TODAY's date (allowed) with a TIME already elapsed** (e.g. 1:00 AM when the real time is ~7 AM UTC) — this is a real, different-from-stored past instant, fully reachable without DB access or waiting a day.

**Role-mode Due Date precedence live-verified both ways on real DB-backed evidence, not just code reading:** explicit date+time → identical shared deadline for every current role holder (checked via the org Status Tracker widget, which shows `<name> · <course> · <date> · Due in N days`). Empty due date → each current holder's own enrollment gets `today + 30 days` (system default `DEFAULT_DUE_WINDOW_DAYS`), confirmed via a specific holder's own Staff-Profile Trainings-table Due Date column (assigned 2026-09-14, due 2026-10-14 — exact 30-day match).

**Renewal-toggle default (`annual`) is real and DB-round-tripped for the standalone assign page — but the WIZARD's own Step 7 has a DIFFERENT, non-annual default.** `AssignPublishClient.tsx`'s `useState` seeds `recurringEnabled: true` / `renewalCycle: 'annual'` for a never-assigned course; `CourseWizard.tsx`'s `INITIAL_FORM_DATA` seeds `recurringEnabled: false` / `renewalCycle: 'none'` (and reminders `[7,3,1]`, vs. the assign page's `[14,3,0]`). Both are real, live-observed defaults (the org's wizard-authored course opened with renewal OFF and 7/3/1 reminders; a course only ever touched via the standalone page opened with renewal ON/Annual and 14/3/0). Not a bug per the stories' own scope (which is specifically about the assign-page default), but a genuine cross-surface inconsistency worth a product call — flag if a future story asks about wizard-time defaults specifically.

**Minor cosmetic finding (ISSUE-1, low severity):** the billing-gate modal shown from "Assign to staff" on `/dashboard/courses` shares its copy with the "Create Course" trigger — always says "A plan is required to **create** courses" even when the trigger was assigning an *existing* course. Mechanism (real explanatory dialog, not a silent bounce) is correct per `CoursesListClient.tsx`'s `onSelect: () => { if (!hasBilling) { setShowBillingGate(true); return; } router.push(...) }` — only the wording is wrong. Could not be clicked live this round (see next note).

**Coverage gap, disclosed not fabricated: the "billing gate explains itself when clicking Assign on an unbilled org" criterion could only be code-verified, not click-tested live.** Reaching `hasBilling === false` while an assignable (non-`isGlobalCatalog`) course row still exists requires an org that HAD active billing + an authored/adopted course and then LOST billing — unreachable from a fresh self-serve org (course creation itself is billing-gated, and the global-video-catalog fetch that could otherwise populate the list is ALSO gated behind `hasActiveBilling` in `listGlobalVideoCatalogCourses`'s caller). Deliberately did not pause/cancel the durable B4 fixture's real Stripe subscription to force this (shared fixture other rounds depend on; product's pause is deferred-to-period-end anyway per [[product-decisions-2026-08-27]], so it wouldn't even flip immediately; and the environment's Stripe-checkout classifier block from [[staging-two-facility-fixture-recipe]] still looms for any *new* subscription attempt). If a future round specifically needs this reachable, the cleanest path is probably a purpose-built short-lived org: subscribe it, author/adopt one course, then cancel — never touch B4 for this.
