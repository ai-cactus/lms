**Full report:** `qa-reports/2026-09-21-backlog-clearing-batch.md`. Verdict: PASS WITH RISKS across 5 stories.

**New capability confirmed live: an org's own HR can now withdraw its learner from an adopted/global Theraptly video course** (PR in `chore/housekeeping-2026-09-21`, `canWithdrawAssignments`/`removeWorkerAssignment` re-keyed off the learner's org, not the course creator's org). Cross-tenant roster isolation reconfirmed clean on the shared "Personal Conduct Series 1" fixture (HR's "Total Learners" count exactly matched D01's own headcount with zero B4 leakage). Positive control on an org-authored course also passes. Technique: never touch D01 Worker's protected enrolment on that course — assign a *throwaway* learner (D01 CD or D01 Worker2) to withdraw instead, nets to zero residual state.

**CONFIRMED FIX — Finance can no longer reach course detail/preview pages nor see the course table/chart on its dashboard**, even for a course it's personally enrolled on (the original leak scenario, reproduced by assigning Finance to a course live and re-testing). Billing and Owner/HR positive controls all correct. **BUT found a pre-existing (not-this-batch) defect while validating this story: Finance's dashboard aggregate TILES (Total Courses, Total Staff Assigned) numerically disagree with Owner's/HR's for the same org at the same instant** (e.g. 2 vs 4, 1 vs 2) — contradicts the code's own comment "the tile must not change with the viewer's role." Root cause confirmed by reading source: `resolveDashboardScope()`'s `courseWhere`/`liveCourseWhere` (built from `authoredCourseWhere()`, which falls back to `OrgCourseOffering`-tracked adoption for non-`course.read` roles) is used for BOTH the correctly-role-gated course list/chart AND the aggregate counts that were never supposed to vary by role — and `OrgCourseOffering` rows aren't written for video courses reaching an org through the current (post-2026-08-10) delivery mechanism, so any role without `course.read` systematically undercounts. `git log` on `src/lib/dashboard/scope.ts`/`src/lib/course/org-scope.ts` confirms this predates today's 6 PRs. **Tracked as BUG-01 in `docs/local/OPEN-ISSUES.md`.**

**CONFIRMED FIX — notification links no longer navigate off-site** (defense-in-depth `toSafeAppPath`). Worker happy path fully confirmed on both bell and full notifications page (`/worker/trainings`, same origin, correct destination). **BUT found a pre-existing (not-this-batch) UX defect while validating this story: a MANAGER recipient of a `COURSE_ASSIGNED` notification is sent to `/worker/trainings` — a route needing a separate worker-context cookie the manager doesn't have — landing on `/login` while still fully authenticated (session verified intact via an immediate `/dashboard` reload with no re-auth needed).** Root cause: `notifyCoursesAssigned()` in `src/lib/enrollment/notify.ts` hardcodes `linkUrl: '/worker/trainings'` for every recipient regardless of role; this org's own fixture has managers (Clinical Director) personally enrolled in courses, so this isn't a hypothetical. `git log` confirms this predates today's security PRs (#660/#661), which correctly refuse off-site navigation but have no opinion on whether an in-app destination is role-appropriate. Positive control: the SAME manager's "New document uploaded" notification correctly navigated to `/dashboard/documents` — isolates the bug to this one hardcoded linkUrl, not the click-handler security fix. **Tracked as BUG-02 in `docs/local/OPEN-ISSUES.md`.**

**CONFIRMED FIX — worker job-title clear now persists** (`WorkerProfileForm` `|| undefined` → `.trim() || null` fix). Set/persist and clear/persist both proven across a hard, cache-busted reload. **Testing gotcha, self-caught: "Save Changes" opens a "Confirm Changes" dialog — clicking Save alone without the second Confirm click does nothing, and looks exactly like a silent persistence bug** (spent real time chasing this as a false positive before spotting the dialog in a screenshot). Always screenshot immediately after a "Save"-labeled click before concluding a save failed to persist.

**BLOCKED, not FAIL — a manager (Owner and HR both tested) has NO editable Job Title field on their own profile at all.** `/dashboard/profile` → Edit renders "Job Title" as a disabled textbox pre-filled with the role label ("Owner (Organisation Admin)", "HR"), never a real custom value, for every manager-category role checked. This is an acknowledged, unchanged-by-today's-batch gap per the fix PR's own text: "the admin `MyProfileSection` — which never sends `jobTitle` — behaves exactly as before." Distinct from (additional to) the previously-recorded `updateStaffDetails`-has-no-UI-caller finding in [[rbac-directive-round-2026-09-17]] — that one was about editing ANOTHER staff member's job title; this one is about a manager's OWN profile page. Name-change on the same page DOES persist correctly (tested + reverted on D01 Owner).

**Reusable technique reconfirmed:** cache-busting query param (`?cb=<timestamp>`) on a reload is a cheap, reliable way to rule out CDN/RSC caching as a false explanation before concluding a save didn't persist.
