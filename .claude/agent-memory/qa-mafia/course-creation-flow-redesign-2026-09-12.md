**Full report:** `qa-reports/course-creation-flow-redesign.md`. Verdict: PASS WITH RISKS, 19/20 criteria PASS (1 minor cosmetic risk). Tested on staging @ `19b7ca0` (PR #598/#599 landed the redesign).

**CRITICAL, first-ever-proven result: real course generation from a single document completes successfully end-to-end on staging in under 2 minutes**, using real Vertex AI against the real production GCP project (staging's Vertex is deliberately pointed at prod — see the user memory `staging-vertex-hits-production-project`). Automated suites never exercise this (no Vertex creds locally/CI). Poll the wizard itself (not the dashboard "still generating" banner, which other memory notes as unreliable) every ~20s — this run's course auto-advanced from the Step 4 interstitial to real "Step 5 of 7" content well inside 2 minutes on a ~4-page real PDF (`docs/local/Confidentiality Training - Series 1.pdf`, renamed to dodge the known filename-collision bug — see [[staging-claim-verification-2026-09-08]]).

**CRITICAL, first-ever-proven result: the real (non-mocked) Vertex PHI scanner genuinely hard-blocks a PHI-bearing upload.** Built a throwaway DOCX with fabricated-but-realistic PHI (name, DOB, SSN, MRN, diagnosis, address, insurance ID) via the `docx` npm package (pdfkit PDFs still fail this app's parser — see [[learner-view-quiz-and-picker-patterns]], use `docx` instead). Upload produced a real amber toast — "WARNING: Protected Health Information (PHI) detected... This document was not saved." — dropzone returned to empty, Next stayed disabled. Unit tests mock the scanner and e2e uses a regex bypass, so this had literally never been exercised against real Vertex before this run.

**The redesigned wizard is a genuinely different 7-step ladder from the old 9-step one** (`src/components/dashboard/courses/wizardSteps.ts`, keys: category/upload/details/quiz/generate/quizReview/assign). Step 2 (`Step2Upload.tsx`) is now a single-dropzone, single-file upload — no more "select from Document Hub" checkbox UI, no more per-module builder. A prior "create a multi-module course" story is now testing a removed feature — always re-derive acceptance criteria from the current design spec, don't trust a stored PASS on the old flow.

**Role-target picker (`RoleTargetPicker`, D5) mechanics confirmed live, in both mount points (wizard Step 7 "Select by Roles" tab, and course details page "Assigned roles" card / `/assign` page "A whole role" toggle):** dropdown shows `None` (default) → `EVERYONE` (Workers/Learners, Managers checkboxes) → `MANAGERS` (Admin, Facility Supervisor, HR, Clinical Director, Finance) → `WORKERS / LEARNERS` (8 individual roles). Ticking a group checkbox expands to individual removable chips for every role in that group (D4). "Finance" appears ONLY under MANAGERS on live staging — the design doc's own flagged "Figma slip" (Finance duplicated in both groups) is NOT reproduced; already correct.

**The "Assigned roles" card on the course details page disappears entirely once every targeted role is revoked — this is confirmed intentional, not a bug.** Proven via the codebase's own test file `src/components/dashboard/training/TrainingDetails.role-picker.test.tsx`, whose top comment states: "The card ... only render[s] once there is an assignment AND that assignment already targets at least one role ... adding the FIRST role target stays with the assign wizard." To re-add a role target after a full revoke, use the course's own `/assign` page → "A whole role" toggle (same shared `RoleTargetPicker`), not the details page. Don't flag the vanished card as a bug in future rounds — check this test file's comment first if in doubt.

**D6's soft-revoke confirm dialog is real and correctly worded:** unticking a role on the details page opens an `alertdialog` titled "Stop enrolling new staff?" with copy that names the exact enrolled-staff count and states they keep the course — e.g. "Staff who gain Nurse will no longer be enrolled in this course. The 5 already enrolled keep the course, and you can still assign it to people directly." Confirmed both halves of D6 live: existing enrollees' course access and Total Learners count are untouched by a revoke, AND a brand-new staff member subsequently given the same (now-revoked) role does NOT auto-enroll — verified by creating a fresh Nurse hire via Staff Management → Add Staff → "Copy invite link" (see [[staging-two-facility-fixture-recipe]] for that acceptance technique) in a second `playwright-cli` session, then confirming they never appeared in the course's Enrolled Staff table.

**D8/D9/D10 reviewer attribution confirmed live:** publishing via the wizard's "Confirm Course Review" modal correctly pre-fills "Reviewed by" with the real acting session user and, after publish, the course details hero renders exactly `"Approved by: <name> (<role>)"` — e.g. "Approved by: B4 Owner (Owner (Organisation Admin))". Also confirmed the details page correctly threads real non-default values through (pass mark set to 75% in the wizard showed as "Pass mark: 75%" on the details hero, not the 80% default; likewise read time was a real computed "20 min read", not a 10 min placeholder) — a good general technique for future rounds: deliberately change a default value mid-wizard so a later "is this real data or a hardcoded default" check on the details page is unambiguous.

**ISSUE-1 (FIXED):** Step 4's "Pass Mark" field was a bare native number input. It now uses the shared `Stepper`, like "Number of Questions" and "Attempts" (`steps/Step4Quiz.tsx`).
