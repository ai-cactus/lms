**Full report:** `qa-reports/2026-09-22-course-list-status-video-thumbnails.md`. Verdict: PASS WITH RISKS, zero defects — the two "risks" are coverage gaps (no live Draft/Inactive fixture), not bugs.

**`CourseListStatusBadge`** (`src/lib/course/course-list-status.ts` + `CourseListStatusBadge.tsx`) is a *different* status mapping from the existing `courseStatusLabel`/"Active"/"Needs Review" one used on detail pages — deliberately splits `published` by `enrollmentsCount >= 1` into green "Assigned" vs blue "Published". Colors: assigned `#d9fae9`/`#308242`, published `#dbeafe`/`#2563eb`, draft `#fffad1`/`#dc6803`, inactive `#f0f2f5`/`#666d80`. Verified live for Published/Assigned across both D01 and B4 (every row's badge agreed with its own Assigned Staff count, no exceptions). **Draft and Inactive have never had a live fixture on staging** — confirmed again this round (consistent with [[rbac-corrections-round2-2026-09-17]]'s "draft state unreachable via org UI"). If a future round needs to actually SEE these badges, seed a fixture course directly rather than relying on the Create-Course wizard reaching Draft (see below).

**Responsive breakpoints are exactly Tailwind's `sm`(640)/`md`(768)/`xl`(1280).** Assigned Staff hides below `md`; Status column hides below `sm` (badge moves under the title instead, via a second `<CourseListStatusBadge className="sm:hidden">` inline under the course name — not a CSS visibility hack); Description/Date Created hide below `xl`. Confirmed the *exact* 1280px boundary live (1280 shows the column, 1024 hides it).

**Real video thumbnails (`/api/courses/[id]/thumbnail?v=…`)** are proven live on all 4 required surfaces: `/dashboard/courses` Video tab, the "Courses" widget on the plain `/dashboard` (component `MyCoursesTable` — **only reachable when `canSeeGlobalDashboard` is false or `accessibleFacilities.length <= 1`**; a multi-facility org's owner/admin with 2+ facilities gets `GlobalDashboardView` instead and never sees this table — for a single-facility org like D01 every admin role reaches it since `assignment.read` alone doesn't gate it out), `/dashboard/audit-reports` Courses tab, and a staff profile's enrolment table. All returned `200 image/jpeg` with genuinely distinct `content-length` per course (proves real per-course stills, not one shared placeholder wearing different crops).

**Negative-test recipe for the thumbnail route's 401/403, reusable:** 401 is trivial (any URL, no session). **403 is NOT reachable with a normal published global video course** — the route's `isGlobalCatalog` bypass (`isGlobal && status === 'published' && type === 'video'`) makes every published global video course's thumbnail visible to ANY authenticated user regardless of org/enrollment, by design (catalog browsing). To get a real 403 you need a global video course that is **not published** — the `[QA FIXTURE] Do Not Assign` course (`status: inactive`, id `6b191350-62b2-4d66-b9f3-e70647bfb6d7` as of this date) is exactly that and is the standing safe fixture for this. An authenticated user of any real org (not its creator, not enrolled) gets a clean 403 against it.

**System-admin Thumbnail panel** (`/system/video-courses/[id]/edit`) — Upload / Regenerate from video / Remove custom all worked cleanly on staging (ffmpeg present). Regenerate and Upload both resolve to `Source: Custom upload` (same `thumbnailStorageUri` field) — they are NOT visually distinguishable by source label alone; compare `naturalWidth`/`naturalHeight` or the `?v=` cache-buster to prove a real change happened. A non-image file renamed `.png` is rejected server-side with `"The file is not a readable image"` even though the client's `accept`/`file.type` check can't reliably catch a mislabeled file — don't trust the client-side extension check as the real gate, always verify the server error. **`[QA FIXTURE] Do Not Assign` is deliberately never `published`, so it can never appear in any org's course list** — testing "org list reflects the new thumbnail" against this exact fixture would require reactivating it (polluting every org's catalog), which conflicts with its own naming; treat that specific sub-check as provable only via the shared code path + other live courses, not by mutating this fixture's publish state.

Please try again in a moment."). This is inconsistent with [[staging-course-generation-failing]]'s RESOLVED status and worth a quick recheck if a future round needs a fresh course. No orphaned course rows were created by any failed attempt (each fails before a Course row is persisted).
