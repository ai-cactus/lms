**Context:** retest of [[dashboard-facility-consistency-investigation-2026-09-24]]'s read-only investigation, now as a real acceptance-criteria run against PR #689 ("one definition per metric across Global, facility and Status Tracker", commit `d91e1bd5`, merged as `ec559c28`/#689). Full report: `qa-reports/2026-09-24-dashboard-facility-consistency.md` (filename kept, content fully overwritten — the old investigation's per-state tables are gone, only the "fixed since" summary remains).

**All 3 direct contradictions from the 2026-09-24 investigation are fixed:** Facility 1 staff-count (Global table vs facility page) now reconciles exactly (6==6, 2==2, sums to Global's Total Staff Count=8, was 8+2=10 vs 5+1=6 before); Facility 1 training-completion 12%-vs-0% same-metric conflict is gone (the facility page no longer claims a directly-comparable "% completed" figure — it's now the assignment-based Training Coverage donut, a genuinely different metric from Global's completion %, small gap is expected roundoff not a bug); Facility-2 Status-Tracker "at risk" badge 1-off is gone (badge now exactly equals Global's Approaching+Overdue sum for both facilities).

**New defect found — D-1, Training Coverage donut legend mismatch between `/dashboard/training` and the facility-scoped `/dashboard?facility=X` page.** Both pages show the identical widget (same centre "Total Assignments" value, same computation — proven by reconstructing the % from the Courses table's per-course Assigned-Staff × Completion-Rate). The facility-scoped page correctly labels it "Assignments completed / in progress / not yet started". **`/dashboard/training` mislabels the SAME assignment-based numbers as "% of staff who have completed / currently enrolled / yet to begin any course"** — the wording implies a staff-population percentage, but arithmetic proves it's assignment-population (e.g. 8% × 36 total assignments = ~3 completed, matching the courses table; 8% of the actual 8 staff would be a non-integer 0.64 people, so it cannot be staff-based despite the label). Medium severity — number is right, only one page's copy is wrong. Worth checking whichever shared component renders `/dashboard/training`'s variant of the coverage donut for a stale/divergent legend-string prop.

**Part B (roster-transfer test, the acceptance criterion that would have proven "facility attribution = current roster") was BLOCKED, not failed** — staging `/signup` returned "We could not send a verification email" on 3 consecutive attempts (~08:39-08:41 UTC 2026-09-28), confirmed via IMAP that zero mail arrived at the QA inbox that day while historical mail (through 2026-09-22) is present and readable (so IMAP itself is fine — this is a real staging SMTP outage, matching the pattern in [[staging-smtp-outage-and-diagnostic]]). Did not attempt a DB-level bypass (out of self-service scope: no DB/SSH credentials were used). **If this task or a similar one is retried, check SMTP health first** (`scripts/test-smtp.ts` needs to run ON the staging server to read its real env, per its own docstring — can't be diagnosed from this machine without SSH).

**Methodology notes that held up / are worth reusing:**
- The facility-switcher modal's additive-chip trap (documented in [[dashboard-facility-consistency-investigation-2026-09-24]]) did NOT bite this round because each switch started from a clean state (no stale prior selection) — but the fix for it is still: always check the apply-button's "Select N facility/facilities" count before clicking apply, and use the **listbox option** (not just the chip) to explicitly deselect an already-selected facility.
- Reconstructing a "% completed" donut figure from a visible per-course (Assigned Staff × Completion Rate) table is a reliable way to determine whether a coverage percentage is staff-based or assignment-based without needing DB access — reuse this arithmetic-reconciliation trick whenever a dashboard percentage's population (staff vs assignments vs courses) is ambiguous from the UI alone.
- Comparison mode (`?facility=uuid1,uuid2`) is a genuinely distinct code path from the default all-facilities view — confirmed by different microcopy ("Comparing 2 of 2 facilities" / "Showing 2 of 2 selected facilities" vs "Performance overview across all facilities" / "Showing 1 to 2 of 2 facilities") even though the numbers happened to be identical in this 2-facility fixture (comparing 2-of-2 facilities is definitionally the same set as "all facilities"). To force a genuinely partial comparison (e.g. 2-of-3), a third facility would be needed — not available in the current B4 fixture.
