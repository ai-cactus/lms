**Verified PASS 2026-09-14 on staging (`ec05433`).** Full report: `qa-reports/2026-09-14-dashboard-facility-scoping-fix.md`. Pre-fix bug: at 0–1 facilities, `/dashboard` and `/dashboard/training` fell through to a legacy view gated on `createdByOrgUserId`, so a single-facility owner's Total Courses/Total Staff Assigned/Average Grade only counted courses *they personally authored* — a colleague-authored or catalog-adopted course was invisible. Fix makes these org-wide at 0–1 facilities too, matching the always-org-wide Status Tracker below it. Table heading "My Courses" → "Courses" on both `/dashboard` and `/dashboard/training` (worker-facing `/worker/trainings` "My Courses" is unrelated and untouched).

**Two structurally different dashboard templates exist, keyed by facility count, not by role — except a Facility Supervisor always gets the single-facility-style template regardless of the org's facility count.** 0–1 facilities (or any Facility Supervisor, in any org): cards are "Total Courses / Total Staff Assigned / Average Grade" + a "Courses" table + Status Tracker. 2+ facilities (owner/admin/manager roles only): "Enterprise Footprint" (Total Facilities, Total Staff Count) + "Training Velocity" (Ongoing Courses) + Facilities Overview / Priority Risks tables + a facility-scope switcher (`?facility=<uuid>`). **A single-facility supervisor's dashboard trivially "looks" org-wide because facility=org there — that proves nothing about the widening bug.** To actually test "did the widening leak to non-manager roles," you need a REAL multi-facility org and must compare the supervisor's per-course "Assigned Staff" numbers against the owner's org-wide numbers for the *same* courses — on B4 (2-facility), F1 Supervisor's numbers were consistently lower (e.g. 8→6, 5→4, 3→1), proving facility-scoping held.

**"QA D01 Org A LLC" is a reusable single-facility + ALREADY-BILLED fixture — found via `/system` search, not built from scratch.** Confirmed exactly 1 facility (Settings → Facility) and an active paid plan (unlike most other `theraptlyqa+` test orgs, which are unsubscribed — see [[courses-billing-gate]]). Owner `theraptlyqa+d01admin@gmail.com`, colleagues `theraptlyqa+d01hr@gmail.com` / `+d01supervisor@gmail.com` / `+d01finance@gmail.com` / `+d01cd@gmail.com`, workers `+d01worker@gmail.com` / `+d01worker2@gmail.com`. All passwords were stale/unknown and were reset via the standard forgot-password+IMAP flow this run (new passwords not memorized here by design — reset again if needed, cheap and self-service). Before this run it had 2 courses (both attributed to the owner); this run added a 3rd via an HR-initiated assignment to make it a genuine "owner didn't author everything" fixture — see next entry.

**Course "Created by" attribution is INCONSISTENT depending on who performs a catalog/video-course adoption — this is what makes/breaks a "non-owner-authored course" fixture.** When the OWNER assigns a video-catalog course to their org for the first time, the resulting org-instance is attributed to the owner by name ("Created by: <Owner>"). When a NON-OWNER staff member (tested: HR role) performs the identical assign action, the resulting instance is attributed to `system@theraptly.internal` instead. So B4's 6 video courses (all adopted long ago, unknown by whom) all show `system@theraptly.internal`, while D01 Org A's pre-existing "Workspace violence prevention 1" (adopted by the owner) shows the owner's name. **To build a "single-facility, owner-didn't-author-everything" fixture fast: log in as ANY non-owner staff member with assign rights (HR worked) and assign one catalog video course to a worker — the new instance will be system-attributed, satisfying the test condition in under a minute, no AI generation or billing setup needed if the org is already subscribed.**

**Assign-form "Due Date" has no clear/remove affordance once set — a genuine UI gap, unrelated to this fix.** `/dashboard/training/courses/<id>/assign`: Training Schedule and every reminder row can be blanked/removed, but Due Date is a button-triggered calendar with no "Clear" action, and re-clicking the already-selected day does not deselect it. Confirmed blocked from reverting a due-date-only cleanup item this way — everything else (role-target removal, renewal toggle, reminder toggle, individual-enrollment withdrawal) reverts cleanly through the UI.

**Removing a course's last role-target via the Assign page (not just the course-detail page) persists immediately/independently of the "Assign Course" submit button** — the confirmation dialog ("Stop enrolling new staff? … Remove") saves right away. But this also EMPTIES the "Assign To" field, which then DISABLES the "Assign Course" submit button (no target selected) — so if you still need to save other field changes (renewal/reminder toggles) in the same visit, you must first re-add at least one already-enrolled person under "Specific people" (harmless — they're already enrolled, saving just re-confirms them) to re-enable the submit button before those other toggles will persist.
