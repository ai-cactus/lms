**Two distinct "pickers" exist in `/learn/[id]` (`src/app/learn/[id]/LearnClient.tsx`) — don't conflate them when a ticket just says "picker":**
1. **`CourseArticle`'s in-content "Table of Contents"** — right-hand panel, visible only in the default **article** view (not quiz mode). This is the ONLY picker with a `scrollIntoView` call (`document.getElementById('module-{idx}').scrollIntoView(...)`), since all lessons render together in one long-scrolling container.
2. **`CourseRail`** — right-side rail, visible ONLY while inside quiz/quiz-review view (`showSharedLayout = isQuizIndex || (quizStep==='review' && quizResults)`). Clicking a lesson here just swaps `activeIndex` and fully re-renders the content pane (video vs quiz) — no scroll mechanism by design, since it's a view-swap not a long-scroll page. If a "doesn't scroll" report actually means this rail, that's expected behavior, not a bug.
3. **`CourseSlide`'s per-page picker** (left rail, only in **Slide** view) lists `pages` from `splitSlideContent()` for the CURRENT lesson only. **Critically: for video courses, the "View on Slides" toggle is hidden entirely** (`onToggleView={isVideoCourse ? undefined : () => setViewMode('slides')}` in the article-view header) — so this picker is completely unreachable via UI for any video-only course. If reproducing a "#5 shows only some slides"-style ticket, first confirm you're on a TEXT course, or you'll never even reach the component.

**Quiz submit/lockout mechanics (`/api/quiz/[id]/start` and `/submit`), confirmed live on staging 2026-08-26:**
- `handleStartQuiz`/`handleSubmitQuiz` in `LearnClient.tsx` (as of the pre-`7aa3a2f` staging build) POST correctly with real bodies; clicking through 2 valid attempts both returned clean 200s end-to-end (start → 5×save → submit), no alert, correct results screen — **submit failures are NOT reproducible on a happy path with attempts remaining**.
- Once `allowedAttempts` is exhausted, `enrollment.status` becomes `locked` server-side, and **the front-end removes ALL UI paths back into the quiz** (no Start/Retake button renders) — you cannot organically reach a "click Submit and watch it fail" repro via the UI once locked. The only way to see the real `403 QUIZ_LOCKED_MAX_ATTEMPTS` from `/start` is a direct authenticated `fetch()` call (bypassing the UI), which correctly returns that JSON.
- **Test-artifact gotcha:** calling `/api/quiz/[id]/start` via `fetch()` WITHOUT a JSON body throws inside `request.json()` and the route's catch-all returns a generic `500 Internal server error` — easy to mistake for a real bug. The real client always sends `{enrollmentId}`; always match that shape when testing the endpoint directly.
- Fix commit `7aa3a2f` (`fix(learn): surface real quiz errors instead of native alert()`) replaces the 3 native `alert()` calls with an inline `Alert` component and adds the missing `res.ok` check on `/start`'s response — landed on a local branch same-day but not yet deployed to staging as of 2026-08-26. If the local repo's branch/HEAD changes mid-session (e.g. another agent is actively committing), trust **live staging network/UI evidence** over local source reads — local source can be a moving target.

**Course-creation wizard (`/dashboard/courses/create`), for building a multi-module TEXT fixture:**
- 9-step wizard: category → per-module (title/objective/deadline/doc-upload with PHI-checkbox) with "Add module" to append more → assignment target (General/Specific Roles) → AI-generated learning objectives (auto-filled from doc content, editable) + slide count + course deadline → quiz config (title/questions/difficulty/pass-mark/attempts, all auto-filled, editable) → **async generation ("Your course is being created…")** → done.
- **`pdfkit`-generated PDFs fail this app's parser**: `Extraction Failed: PDF Parsing Failed: Command token too long: 128`. **Use `docx` (npm) instead** — DOCX uploads parsed and PHI-scanned successfully every time. See [[document-hub-patterns]] for the general PDF/DOCX fixture-generation recipe; this is an addendum specific to the course-creation wizard's parser (stricter than the Document Hub's own parser, apparently).
- **The async AI generation step can take a very long time** — confirmed *still generating after 21+ minutes* of bounded polling in one run, never observed to complete within that session. Budget accordingly: this is not a fast path for building test fixtures under time pressure. If diagnosing something time-boxed, prefer using/adapting an already-existing course over generating a new one, or kick off generation early and do other testing in parallel while it completes in the background.
- Prebuilt catalog (`/dashboard/courses/prebuilt`, linked from step 1) only offered the same single video course already in the org — no separate text-course prebuilt existed for org "QA D01 Org A LLC" as of 2026-08-26.

**Login button label:** staging's login submit button reads exactly **"Log In"** (capital I), not "Log in" — `getByRole('button', { name: 'Log In', exact: true })`. Update if [[staging-env-access]]'s locator ever drifts.

See also [[watch-through-gate-testing]] for driving a real video lesson to completion via `video.play()` + real-time wait (used here to unlock a video-course quiz gate in ~9.5s for an 8s clip), and [[long-wait-tests-must-stay-synchronous]] — bounded polling loops of `sleep N; playwright-cli ...` inside one Bash call work, but each Bash tool call still has its own ~2min default timeout that bites well before a slow async pipeline finishes; pass an explicit longer `timeout` param on the Bash call itself if you need more than ~3 iterations at 20-40s intervals.

**UPDATE 2026-08-26 (same day, follow-up run) — course generation on this org is NOT slow, it FAILS, consistently and fast, with zero user-facing error.** What looked like a 20+ minute hang in the first pass turned out to be a stuck "still being generated" banner masking a real failure: checking `/dashboard/courses/queue` (an internal `prisma.job` viewer, **not linked from any nav item** — only found by reading `src/app/dashboard/courses/queue/page.tsx`) showed both `GENERATE V46_COURSE` jobs as **"Failed."** A second, independent course-creation attempt (fresh docs re-uploaded) reproduced the same 2/2 failure in **under 1 minute** — and `/dashboard/courses` still showed "still being generated" 2+ minutes after that. **Lesson: don't trust the "still being generated" banner as a liveness signal at all — check `/dashboard/courses/queue` directly instead of polling the Courses page.** The `Job` model has a `result: Json?` field that likely holds the failure reason, but no UI surface renders it and there's no API to fetch it — diagnosing the actual root cause needs DB/log access this agent doesn't have by default. Filed as a CRITICAL issue in `qa-reports/2026-08-26-learner-view-repro.md` (ISSUE-1); blocked live #3/#5 verification entirely since no working multi-module TEXT course could be produced on this org as of that date.
