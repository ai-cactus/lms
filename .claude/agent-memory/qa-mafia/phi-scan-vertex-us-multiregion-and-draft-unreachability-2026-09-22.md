**Full report:** `qa-reports/2026-09-22-phi-scan-vertex-us-multiregion.md`. Verdict: PASS WITH RISKS. PR #671 itself (move Gemini calls to the Vertex US multi-region endpoint / gemini-3.1-flash-lite, to stop PHI scans failing closed on 429s) is fully proven: 4 live scans this round (1 clean, 3 PHI-positive), zero "We could not verify this document for PHI" fail-closed messages, zero Vertex 429s. This directly follows up the flakiness recorded in [[course-list-badges-and-video-thumbnails-2026-09-22]] ("We could not verify..." seen twice that same day, ~10:47-11:00 UTC) — not reproduced at all this round.

**CRITICAL, code-confirmed: a `Course` DB row is not created until "Publish Course" is clicked, and a structurally-successful generation is code-guaranteed to land as `published`, never `draft`.** Read directly from `src/components/dashboard/courses/CourseWizard.tsx` + `src/app/actions/course.ts`: `createFullCourse` (the only write that persists a `Course` row) runs exclusively inside `handlePublish`, reachable only from Step 7's "Publish Course" button. Steps 5-6 (content/quiz review) render real generated content, but it lives only in client React state plus a `GENERATE V46_COURSE` job record until Publish — there is **no wizard resume mechanism** (confirmed: reopening `/dashboard/courses/create` always restarts fresh at Step 1, no localStorage wizard state survives, no job-linked resume UI). `assessCourseQuality()` sets `reviewRequired: true` (→ `status: 'draft'`) ONLY on a genuine content shortfall (zero quiz questions, zero slides, a flagged/ambiguous quiz question, or a too-short source doc) — a normal successful generation (the kind Story 1/3's fixture always produces) will therefore always persist as `published` the instant Publish is clicked. **You cannot force a draft by emptying the quiz in Step 6 either**: `isNextDisabled()` for the `quizReview` step returns `true` once `generatedContent.quiz.length === 0`, so Next Step (and Publish) become unreachable at exactly zero questions. This sharpens (not just reconfirms) [[course-list-badges-and-video-thumbnails-2026-09-22]]'s "no live Draft/Inactive fixture" and [[rbac-corrections-round2-2026-09-17]]'s "draft state unreachable via org UI": it's not merely rare, it is structurally prevented for any successful generation. Producing a real Draft-badge fixture needs either a direct DB seed or a deliberately-engineered content shortfall (e.g. an unusably short/garbled source doc) — get a product/QA ruling on which is acceptable before attempting again.

**A mid-task browser-session + scratch-directory restart loses an in-progress, unpublished wizard generation with zero recovery path** — confirmed the hard way this round (Story 3's first pass reached Step 7 with full content, the session restarted, and the course was simply gone — verified absent via BOTH `/dashboard/courses` Reading tab search and `/dashboard/audit-reports` Courses tab raw-status list, both showing an unchanged pre-existing course count). If a future round needs to survive a possible restart mid-wizard, either finish Publish before risking it or accept the redo cost — there is no partial-save to check first.

**Recipe for genuinely exercising the AI PHI-scan path with a custom fixture (reliable, code-verified):** build a throwaway DOCX via the `docx` npm package (already in repo `node_modules`; run the build script from inside the repo directory itself — `import 'docx'` fails to resolve when run from a plain `/tmp` script) containing PHI that is real/contextual but matches **none** of `src/lib/documents/piiPatterns.ts`'s high-confidence patterns: no dashed SSN (`\d{3}-\d{2}-\d{4}`), no `@`-style email, no separator-formatted phone (needs dashes/dots/spaces/parens — a bare 10-digit run like `5551234567` is safe). A name + a DOB spelled out in words + a street address + an unlabeled multi-digit record number + an unformatted phone, kept over 50 chars (`MIN_SCAN_LENGTH`), reliably reaches `scanChunkWithAI` and gets a real PHI-found block (`"WARNING: Protected Health Information (PHI) detected..."`), distinct from the fail-closed `"could not verify"` string. Server-action duration for this path was ~2.1s this round vs ~1.4s for an SSN-triggered local-regex block — real but not a dramatic enough gap to use timing alone as path evidence; rely on the content construction (verified against the regex source) as the primary proof, timing as secondary.

**The repo's purpose-built AI-path fixture `docs/local/test-fixtures/policy-with-phi.pdf` (built with `pdfkit`, per its own README) now fails at PDF text-extraction on staging** — `"Extraction Failed: PDF Parsing Failed: bad XRef entry"`, before any PHI scan runs. It worked on 2026-08-14 per `docs/local/RUNBOOK.md`; this is a fixture-quality regression (or borderline-fragile pdfkit output), not a PHI-scanner defect — extraction is upstream of `phiScanner.ts` entirely. Consistent with existing guidance ([[document-hub-patterns]]) to prefer `docx` over `pdfkit` for fixtures; this fixture should be rebuilt as a DOCX. Its clean sibling `policy-clean-no-phi.pdf` was not retested this round — check it before relying on it.

Not pursued further this round since other live-UI evidence (Reading tab search + Audit Reports raw-status tab) was already conclusive.
