**Gmail IMAP `STATUS INBOX (MESSAGES ...)` count is unreliable/stale for freshly-arrived mail — don't poll it to decide "has my email arrived yet."** During the 2026-07-27 staging fix-verification run, `STATUS INBOX (MESSAGES UNSEEN)` kept reporting the same total (`99`) even after successfully fetching UIDs well past that number (confirmed up to UID 103). Use `UID SEARCH UID <lastKnownUid>:200` (or similar open-ended range) to discover new arrivals instead, and/or just retry a direct `FETCH ... SECTION=HEADER.FIELDS` on the next expected UID with a short poll/backoff loop — that reliably returns once the message exists, independent of what `STATUS` reports. The curl IMAP command pattern itself (`imaps://imap.gmail.com:993/INBOX;UID=N;SECTION=...`) is otherwise accurate and fast (seconds, not minutes) once the message has actually arrived — see [[qa-test-gmail-inbox]] for the base credential/parsing pattern (quoted-printable body decoding via `python3 -c "import quopri; ..."` is required to extract reset-password/OTP links and codes — raw `grep` on the wire body will miss `=3D`/soft-line-break-encoded URLs).

**Password-reset ("Forgot your password?") flow appears to clear/disable an account's existing 2FA enrollment (staging, confirmed 2026-07-27).** An account (`+p1owner`) that a prior QA run had left with email-OTP 2FA enabled logged in with **no MFA challenge at all** immediately after a password reset via this run — Profile → "Two Factor Auth (2FA)" tab confirmed "2FA is disabled on your Theraptly account." This is plausibly deliberate security behavior (a password compromise/reset scenario reasonably invalidates a stale 2FA factor tied to the old credential), but it means **you cannot assume 2FA state survives a password reset across QA runs** — always check the 2FA tab before assuming a login will (or won't) need an OTP, and re-enroll via "Set up 2FA" if a story specifically needs 2FA-gated login/OTP-copy behavior. Re-enrolling is itself a good source of a fresh, real OTP email if you need to inspect its exact wording (see below).

**Rate limits are IP-keyed, not per-email, on `password-reset` (`checkRateLimit('password-reset:${ip}', 5, 600)` in `src/app/actions/auth.ts`).** Requesting resets for 6+ different test accounts back-to-back from the same session can silently rate-limit the later ones — the endpoint still returns the generic "If an account exists... we've sent a link" copy regardless (security best practice: never reveals rate-limiting either), so a "missing" reset email might just be silently dropped by this limiter, not a delivery failure. If an expected reset/OTP email doesn't show up within a few seconds, wait out the full 600s window from your *first* request in the batch before concluding something is broken, then retry.

**Testing server-side validation behind a client-side-only gate (e.g. a submit button `disabled={!isValid}` with no matching server enforcement, or vice-versa when you need to prove the server independently rejects bad input): dispatch the form's native `submit` event directly via `page.evaluate`, bypassing the disabled button.** Pattern that worked cleanly on a React form using `onSubmit={handleSubmit}` + a separate confirm-dialog step:
```js
await page.evaluate(() => {
  const form = document.querySelector('form');
  form.requestSubmit ? form.requestSubmit() : form.dispatchEvent(new Event('submit', {bubbles:true, cancelable:true}));
});
```
`form.requestSubmit()` (or a manually dispatched `submit` Event as a fallback) fires the component's real `onSubmit` handler regardless of whether the associated submit button is currently `disabled` — the `disabled` attribute only suppresses a *button-click-triggered* submission, not a directly-dispatched form submit. If the app's flow is `onSubmit → open confirm dialog → onConfirm → actual server call` (a common pattern here), the confirm dialog will open normally and you can proceed to click its own (usually not gated) confirm button to reach the real server action call — giving you a completely legitimate way to verify "does the server actually reject this on its own" without ever fabricating a raw HTTP request or forging server-action encoding. Confirmed working live 2026-07-27 to verify `updateProfile`'s empty-name rejection (`src/app/actions/user.ts`) independent of `ProfileForm.tsx`'s `isValid` gate.

See [[document-hub-patterns]] for a related "the fix only touched the server action, not the page that actually calls a *different* code path" gotcha found in the same run — always check which component/action a UI screen is genuinely wired to before assuming a server-side fix closes a UI-visible finding.
