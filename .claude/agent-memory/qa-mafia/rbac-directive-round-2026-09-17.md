**Full report:** `qa-reports/2026-09-17-staging-rbac-multi-tenancy-release.md`. Verdict: PASS WITH RISKS, 8 stories, most PASS but 2 real FAILs and 2 BLOCKED-by-missing-UI. Source docs for the ruling itself: `docs/local/RBAC-founder-answers-2026-09-15.md` (the "why", cite this over prose) and `docs/local/RBAC_for_multi-tenancy-updated.md` (the matrix table itself) — both are excellent primary sources, read them before designing acceptance criteria for any future RBAC-adjacent story on this codebase.

**Archive-not-delete (Q24) is real and works end-to-end for courses, documents, and the auditor catalogue/export agreement** — confirmed live: archived items vanish from lists/search, a direct URL 404s cleanly, the auditor's on-screen course count exactly matched a downloaded CSV export (both read off `rawPrisma`, see `db/index.ts`'s 4-consumer allowlist comment). **BUT the Delete confirmation dialogs (both course and document) still say "permanently remove… cannot be undone"** — stale pre-archive copy, contradicted the founder's own Q24 ruling. **Since fixed:** that copy now appears only in the `/system` DeleteUserModal.

**Three defects found this round, all since FIXED:**
- **Archived-course "Continue" 404.** `getCourseById` didn't carry the enrolled-learner carve-out that `get-learn-payload` had, so `/worker/courses/[id]` 404'd for an archived course while `/learn/[id]` worked. Fixed in `fcc7c1b2`: `course.ts` now uses `rawPrisma` for enrolled learners.
- **HR blocked from quiz results.** `getEnrollmentWithResults` required the caller to be the literal course author, contradicting Q6. Fixed in `fcc7c1b2` (`enrollment.ts`).
- **No UI called `updateStaffDetails`.** It had a dead `canEdit` variable. Fixed by PR #637: `ChangeRoleModal.tsx` and `EditProfileModal.tsx` now call it.

The positive-control technique that proved the HR defect is recorded under "Feedback on methodology" below.

**Withdraw-assignment UI location, reconfirmed and refined:** "Withdraw assignment" is reachable ONLY from a course's own detail page → Enrolled Staff table → per-row kebab — NEVER from the Staff Profile page's per-course actions menu (that one only ever offers "Assign Retake", disabled or not, regardless of whether the course is org-authored or video/catalog). This refines/corrects the older note in [[course-delete-and-withdraw-mechanics]] which implied the split was about org-authored vs. video-adopted courses — it's actually about WHICH PAGE you're on, not the course type. A genuinely org-authored course ("Upholding Confidentiality…", `isOrgAuthored: true`) still shows only "Assign Retake" from the Staff Profile page.

**Assign-course flow has a real, easy-to-miss second step:** clicking the modal's "Assign Course" submit on the course-selection dialog does NOT complete the assignment by itself — it opens a SECOND "Set Completion Deadline" dialog (optional due date + 30-days/6-months/1-year quick buttons) that must ALSO be confirmed via its own "Assign Course" button before the enrollment actually lands. Missing this second click silently no-ops the whole assignment (confirmed by reproducing the miss once, then redoing it correctly and seeing the enrollment appear).

**Story-8 removal+re-invite is a clean, reliable way to PROVE retention with real evidence:** remove a staff member with real progress (a completed+certificated course AND an in-progress one) → confirm login blocked with a real disambiguating message ("Your access to this organization has been removed…") and a live session gets killed mid-session → re-invite the SAME email → accept via the invite-acceptance flow (asks for a fresh name+password even though the person existed before — this is expected, not a bug) → log in → both the exact same completion status AND the exact same Certificate ID reappear untouched. Confirms commit `243375f4` end-to-end, not just at the unit-test level.

**Live self-service password-reset via IMAP scales fine across ~10 accounts in one session** (D01: admin/hr/finance/cd/worker/worker2; B4: F1sup/F2sup) using a raw Node `tls` socket IMAP client (no npm package needed) — see the script pattern: LOGIN → SELECT INBOX → `UID SEARCH SINCE <date>` to enumerate, then `UID FETCH <uid> (BODY.PEEK[HEADER.FIELDS (SUBJECT TO DATE)])` to disambiguate by recipient (`To:` header) when many reset emails land in the same catch-all inbox at once, then `BODY.PEEK[TEXT]` + Python `quopri` decode to extract the actual reset link. A `playwright-cli fill` immediately followed by an `eval` read-back of `.value` is a good sanity check when a submit button stays mysteriously disabled — in one case here it caught a genuinely-required "Facility type" field (pre-existing, unset since before this test) blocking a save with an easy-to-miss inline validation message, not an RBAC bug.

**Feedback on methodology, confirmed by the orchestrator as the right call — keep doing both of these:**
1. **Proving a permission-defect with a positive control (the same URL/action succeeding for a role that SHOULD have access) is what turns "role X couldn't see page Y" from an ambiguous observation into a defect finding.** This is what made ISSUE-4 (HR quiz-results) land as a real, actionable bug rather than "HR hit a 404" — Owner succeeding on the identical URL isolated the cause to the specific authorization check, not the page's RBAC gate or missing data. Reach for this pattern any time a role appears blocked from something the matrix says they should have.
2. **Distinguish "a correctly-authorized server action with no UI caller" from "an RBAC gate that's wrong."** The `updateStaffDetails`/dead-`canEdit`-variable finding in this run (since shipped in PR #637) was deliberately reported as its own cross-cutting note, not folded into Stories 5/6's pass-fail table as a straightforward defect — and the orchestrator confirmed this framing was correct and explicitly excluded it from the ISSUE-1..4 fix branch ("a missing feature needing product scoping, not a gate defect... would have quietly turned a bug-fix PR into a feature PR"). Keep drawing this line sharply in future reports: a dead/unwired authorization check is a scoping question for the orchestrator/user, not automatically a bug to bundle with live gate defects.
