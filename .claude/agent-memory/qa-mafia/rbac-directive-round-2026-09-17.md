**Full report:** `qa-reports/2026-09-17-staging-rbac-multi-tenancy-release.md`. Verdict: PASS WITH RISKS, 8 stories, most PASS but 2 real FAILs and 2 BLOCKED-by-missing-UI. Source docs for the ruling itself: `docs/local/RBAC-founder-answers-2026-09-15.md` (the "why", cite this over prose) and `docs/local/RBAC_for_multi-tenancy-updated.md` (the matrix table itself) — both are excellent primary sources, read them before designing acceptance criteria for any future RBAC-adjacent story on this codebase.

**Archive-not-delete (Q24) is real and works end-to-end for courses, documents, and the auditor catalogue/export agreement** — confirmed live: archived items vanish from lists/search, a direct URL 404s cleanly, the auditor's on-screen course count exactly matched a downloaded CSV export (both read off `rawPrisma`, see `db/index.ts`'s 4-consumer allowlist comment). **BUT the Delete confirmation dialogs (both course and document) still say "permanently remove… cannot be undone"** — stale pre-archive copy, contradicts the founder's own Q24 ruling, cheap fix.

**CRITICAL live defect — an enrolled learner's ONLY UI path to resume an in-progress ARCHIVED course is a dead 404.** `/worker/trainings` → "Continue" → `/worker/courses/[id]/page.tsx` calls `getCourseById()`, which is NOT one of `db/index.ts`'s 4 documented un-filtered (`rawPrisma`) consumers (only video-sweep-worker, auditor-export-worker, system-admin, and **get-learn-payload** are). So the overview/preview page 404s for an archived course even though the real lesson content live at `/learn/[id]` (which DOES use get-learn-payload) works perfectly — full lesson text, quiz, Attest, and certificate issuance all completed successfully via direct URL. A learner has no way to discover `/learn/[id]` on their own; the only reachable button (`Continue`) is broken. Control-tested: the identical click path on a non-archived course works fine, isolating this to archived courses specifically. This is exactly the scenario the release's own commit message (`f621babf`) claims to have solved ("an enrolled worker must still be able to open it") — the carve-out just wasn't wired into the actual page a learner clicks through.

**CRITICAL live defect — HR cannot view a named staff member's quiz results, despite the founder's explicit Q6 ruling ("HR can build quizzes and view results") and HR holding `assessment.read`.** `getEnrollmentWithResults` (`src/app/actions/enrollment.ts`) gates on `enrollment.course.createdByOrgUserId === session.user.organizationUserId` — i.e. the caller must be the LITERAL course author, a pre-Q6/pre-org-ownership authorship check that other functions (deleteCourse, enrollUsers) already migrated off of. Positive control on the SAME URL: Owner (who happens to be the course's author) gets 200 + real content; HR (not the author) gets a clean 404 via the page's Q26 catch-block (`error.message === 'Access denied'` → `notFound()` — that 404-shaping mechanism itself is working exactly as designed, it's the underlying `isCourseCreator` check that's wrong). In practice HR will almost never be the literal author of a video/catalog course, so this closes off the Q6 grant for the overwhelming majority of real courses. See [[founder-rbac-directive-2026-09-15]].

**CROSS-CUTTING — no UI anywhere in the product calls `updateStaffDetails` (staff name/job-title edit + re-role), even though the server action, `STAFF_PROFILE_ACTOR_ROLES`, and `canChangeRole`/`GRANTABLE_ROLES` are all correctly wired and presumably unit-tested.** `StaffProfileClient.tsx` computes `canEdit = STAFF_PROFILE_ACTOR_ROLES.includes(viewerRole)` and then NEVER uses that variable to gate any rendered control — dead code. Live-confirmed for both HR (viewing a worker) and Facility Supervisor (viewing an F1 worker): the Staff Profile page's only possible action buttons are "Change Facility" and "Assign Course" (gated by `canAssignCourses || canChangeFacility`); the kebab only offers "Remove Staff"; the per-course actions menu only offers "Assign Retake"/"Withdraw assignment". This means "HR can re-role staff" (Q11) and "Supervisor can edit name/job title" (Q2) are **not exercisable by any real user today** — a genuine, sizeable gap that's easy to miss because every server-side test passes. Flag this loudly in any future round that touches Staff Management.

**Withdraw-assignment UI location, reconfirmed and refined:** "Withdraw assignment" is reachable ONLY from a course's own detail page → Enrolled Staff table → per-row kebab — NEVER from the Staff Profile page's per-course actions menu (that one only ever offers "Assign Retake", disabled or not, regardless of whether the course is org-authored or video/catalog). This refines/corrects the older note in [[course-delete-and-withdraw-mechanics]] which implied the split was about org-authored vs. video-adopted courses — it's actually about WHICH PAGE you're on, not the course type. A genuinely org-authored course ("Upholding Confidentiality…", `isOrgAuthored: true`) still shows only "Assign Retake" from the Staff Profile page.

**Assign-course flow has a real, easy-to-miss second step:** clicking the modal's "Assign Course" submit on the course-selection dialog does NOT complete the assignment by itself — it opens a SECOND "Set Completion Deadline" dialog (optional due date + 30-days/6-months/1-year quick buttons) that must ALSO be confirmed via its own "Assign Course" button before the enrollment actually lands. Missing this second click silently no-ops the whole assignment (confirmed by reproducing the miss once, then redoing it correctly and seeing the enrollment appear).

**Story-8 removal+re-invite is a clean, reliable way to PROVE retention with real evidence:** remove a staff member with real progress (a completed+certificated course AND an in-progress one) → confirm login blocked with a real disambiguating message ("Your access to this organization has been removed…") and a live session gets killed mid-session → re-invite the SAME email → accept via the invite-acceptance flow (asks for a fresh name+password even though the person existed before — this is expected, not a bug) → log in → both the exact same completion status AND the exact same Certificate ID reappear untouched. Confirms commit `243375f4` end-to-end, not just at the unit-test level.

**Live self-service password-reset via IMAP scales fine across ~10 accounts in one session** (D01: admin/hr/finance/cd/worker/worker2; B4: F1sup/F2sup) using a raw Node `tls` socket IMAP client (no npm package needed) — see the script pattern: LOGIN → SELECT INBOX → `UID SEARCH SINCE <date>` to enumerate, then `UID FETCH <uid> (BODY.PEEK[HEADER.FIELDS (SUBJECT TO DATE)])` to disambiguate by recipient (`To:` header) when many reset emails land in the same catch-all inbox at once, then `BODY.PEEK[TEXT]` + Python `quopri` decode to extract the actual reset link. A `playwright-cli fill` immediately followed by an `eval` read-back of `.value` is a good sanity check when a submit button stays mysteriously disabled — in one case here it caught a genuinely-required "Facility type" field (pre-existing, unset since before this test) blocking a save with an easy-to-miss inline validation message, not an RBAC bug.

**Feedback on methodology, confirmed by the orchestrator as the right call — keep doing both of these:**
1. **Proving a permission-defect with a positive control (the same URL/action succeeding for a role that SHOULD have access) is what turns "role X couldn't see page Y" from an ambiguous observation into a defect finding.** This is what made ISSUE-4 (HR quiz-results) land as a real, actionable bug rather than "HR hit a 404" — Owner succeeding on the identical URL isolated the cause to the specific authorization check, not the page's RBAC gate or missing data. Reach for this pattern any time a role appears blocked from something the matrix says they should have.
2. **Distinguish "a correctly-authorized server action with no UI caller" from "an RBAC gate that's wrong."** The `updateStaffDetails`/dead-`canEdit`-variable finding in this run was deliberately reported as its own cross-cutting note, not folded into Stories 5/6's pass-fail table as a straightforward defect — and the orchestrator confirmed this framing was correct and explicitly excluded it from the ISSUE-1..4 fix branch ("a missing feature needing product scoping, not a gate defect... would have quietly turned a bug-fix PR into a feature PR"). Keep drawing this line sharply in future reports: a dead/unwired authorization check is a scoping question for the orchestrator/user, not automatically a bug to bundle with live gate defects.
