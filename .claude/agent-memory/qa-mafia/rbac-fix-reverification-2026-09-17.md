**Full report:** `qa-reports/2026-09-17-staging-rbac-fix-reverification.md`. Verdict: PASS, all 3 target fixes confirmed live with positive controls. Follows [[rbac-corrections-round2-2026-09-17]], which reported these same 3 things as defects.

**Methodology correction, confirmed important:** the prior round's "audit export completes but delivers no file" was NOT a bug — there is no file artifact by design (`Job.result` stores JSON; the download route serialises on request only when "View Report" is clicked). The prior round's own network log never showed a `GET .../download` request, meaning the click never happened. **Before asserting a download did/didn't happen, always cite the actual `GET .../download?format=<fmt>` request/response, not just the completion toast.** The button is labelled "View Report" with a document icon but downloads a CSV — plausibly why the original miss-click happened; this mislabel is a known, deliberately-deferred design item (conflicts with an approved Figma frame per the PR notes), not re-flagged as a defect.

**CONFIRMED FIX — empty audit export now gets its own distinct state.** A per-worker export for a worker with 0 assigned/0 completed (e.g. D01 CD before any role change) returns `{"status":"completed","message":"No records matched","rowCount":0}` from the status endpoint, and the UI shows **"No records matched this date range" / "The export finished, but there was nothing to report."** with **no download action offered anywhere in the DOM** — structurally distinct from the "Report Ready" banner. A real export (D01 Worker2: 2 assigned/1 completed) → View Report → `GET /api/auditor/export/<jobId>/download?format=csv` fires and returns 200 with exactly 2 CSV rows, matching the on-screen Assigned/Completed counts exactly (1 `attested` row = the 1 completed).
