**Full report:** `qa-reports/2026-09-21-reading-course-slide-editor-batch.md`. Verdict: PASS WITH RISKS. Stories 1/2/4/5 clean PASS; Story 3's explanation-copy fix is genuinely correct but surfaced Issue 1 below.

**Byte-level "everything else stayed untouched" technique, reusable for any future slide/content-editor claim.** Wrote a `playwright-cli run-code` script that walks the entire deck via the "Next" button (across module boundaries too — Next at a module's last slide advances into the next module automatically), dumping `nav[aria-label=Slides]`'s sibling container's `innerHTML` at every slide into a JSON array, before and after the edit+save+reload. Diffing the two arrays index-by-index is a much stronger proof than spot-checking a few slides — on an 18-slide/4-module deck it caught that exactly 1 slide differed, and stripping the injected marker text from that one slide's HTML made it byte-identical to its own "before" state, with the markup skeleton (`html.match(/<[^>]+>/g).join('')`) unchanged too. `run-code` scripts must be `async page => { ... }` with **no trailing semicolon** — the whole thing gets wrapped in `(...)`, so a trailing `;` becomes a syntax error inside the parens.

**Locked-region proof for a "some regions are editable, some aren't" claim: check `contenteditable` on the actual DOM node, not just visual absence of a textbox border.** `page.evaluate` querying `.slide-scenario` (or whatever the container class is) for every descendant, filtering to elements whose class matches the feature's naming convention (`badge`/`tag`/`scenario`) plus anything with `contenteditable !== null`, gives an unambiguous locked/editable map in one call. Confirmed this app's pattern: locked elements simply have no `contenteditable` attribute at all (not `contenteditable="false"`); editable ones carry `class="slide-editable-text ..."` and `contenteditable="true"`.

**New CRITICAL/HIGH finding — "Add new question → Generate with AI" (course-creation wizard Step 6) hits a Cloudflare 524 gateway timeout in ~2 of 3 attempts, each after 90-110+s.** This is a *synchronous* browser-awaited call (unlike full-course generation, which is an async job the client polls — see [[course-creation-flow-redesign-2026-09-12]] for that pattern's ~2min budget). Console shows `Failed to load resource: 524` + `Failed to call AI generation: ... An unexpected response was received from the server.`, and the UI's only feedback is a generic native `alert("An unexpected error occurred.")` — no retry affordance, no indication whether anything was created. **RESOLVED by PR #657:** the cause was the Vertex retry budget overrunning Cloudflare's ~100s gateway limit, NOT the `maxOutputTokens` bump. See [[vertex-retry-budget-fix-verification-2026-09-21]]. **When it does succeed** (1 of 3 attempts, ~75-80s), the explanation is genuinely correct and renders exactly like the AI-generated originals (`✓ Correct: ...`, no ✕ items — matching the PR's declared `incorrectOptions: {}` tradeoff on this path). "Regenerate Quiz" (the whole 5-question set) succeeded in its only attempt, ~35s — worth more repeat testing in a future round to see if it shares the risk or is genuinely faster.

**Course-creation wizard gotcha confirmed again, more precisely than before: the "I verify this document contains no PHI" checkbox must be checked BEFORE the file is dropped/selected, not after.** Checking it after a successful upload silently resets the dropzone to empty with no error message — looks exactly like the upload failed. Order: check the box first, then click the dropzone and pick the file.

**Password-reset via forgot-password + IMAP: `source .env.local` alone does NOT export vars to a `node -e` subprocess — use `set -a; source .env.local; set +a`.** Cost one wasted debugging cycle (IMAP LOGIN kept failing with AUTHENTICATIONFAILED even though the .env.local values were correct, because `process.env` in the spawned node process was empty). Also: IMAP `SEARCH SINCE` needs the literal IMAP date format `DD-Mon-YYYY` (e.g. `21-Sep-2026`), not an ISO-ish string — the wrong format returns zero UIDs with no error, which looks identical to "the email hasn't arrived yet."
