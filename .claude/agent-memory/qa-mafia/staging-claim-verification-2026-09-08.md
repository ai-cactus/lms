**Full report:** `qa-reports/2026-09-08-staging-claim-verification.md`. This was a claim-verification run (re-checking specific project-notes assertions against live staging), not a fresh story run — 4/4 claims CONFIRMED, two with material nuance.

**CONFIRMED, finally, after 4 QA rounds (2026-09-03 → 2026-09-08): Draft→Published-on-assignment (`publish-on-assign.ts`) works live end-to-end, including the mandatory control case.** Recipe that worked: duplicate an `isOrgAuthored` course twice (Copy A, Copy B), assign ONLY Copy A via the **target staff member's own Staff Profile → Assign Course** button (not the course's own `/assign` page — that path already published as a side effect in earlier testing, which is why the repro insists on the profile-page path), leave Copy B untouched. Copy A → `published`/"Active"; Copy B → stays `draft`/"Draft". Verified two independent ways: the course-detail page's status badge (`courseStatusBadge()`, `src/lib/course/course-status-label.ts` — "Active" for published, "Draft" for draft+!reviewRequired) AND Audit Reports → Courses tab's raw `course.status` text column — both agreed. **Audit Reports → Courses tab is the single best place to read a course's raw lifecycle status** (shows literal `draft`/`published`/`inactive`, not a relabeled badge) — use it whenever a claim needs the DB-level status, independent of any UI label-mapping bug.

**Duplicate (`7b1b9b5`) is CONFIRMED working on org-owned (`isOrgAuthored`) courses — 2/2 clean, zero 500s.** But the "adopted/global course" half of any future claim about Duplicate needs a corrected mental model: `buildRowActions` in `CoursesListClient.tsx` gates Duplicate (and Delete) on `course.isOrgAuthored`, and **adopted/catalog courses never get that action offered at all** (not "fixed to work," but "removed from the menu entirely" — by design, since `duplicateCourse` can only fork a course the org itself authored). A true `isGlobalCatalog` row gets an EMPTY kebab menu (zero actions); an adopted-but-not-authored row (e.g. a video pulled from the catalog) gets Assign/View Source/Rename but never Duplicate/Delete. In this fixture org, 5 of 6 video courses are adopted-not-authored and 1 ("Personal Conduct Series 1") is true global-catalog — useful known specimens if a future round needs one of each type again.

**NEW BUG found (not part of the claims, discovered while building the Claim-1 fixture): the Create-Course wizard's document-matching logic can silently attach a DIFFERENT USER'S document to your course, causing "Generation Failed — Document not found."** Root cause: `Step2Modules.tsx`'s `handleFilesSelected` calls org-wide `getDocuments()` (scoped by `organizationId`, returns every user's uploads) and matches its own fresh upload back **by filename only** (`.find(doc => doc.filename === file.name)`) — if ANY other user in the org has ever uploaded a document with the identical filename, the wrong doc can be picked, and the later generation step (`course-ai-v4.6.ts`) correctly scopes by `organizationUserId` and fails to find it under the current user. **Reproduced 2/2 times using the well-known fixture `docs/local/Confidentiality Training - Series 1.pdf`** (this exact filename had already been uploaded by a different account in an earlier QA round) — every future round that reaches for this fixture file on the "QA B4 Multi-Facility Org LLC" org will hit this. **Workaround: rename the file to something unique before uploading** (e.g. copy it to `QA-Verification-Source-<date>.pdf` in the scratchpad first) — generation then succeeds first try. Flag this fixture-file collision risk in any future wizard-course-creation task on this org.

**Billing plan-card prices are showing "Price unavailable" on ALL 9 cells (Starter/Growth/Pro × Monthly/Quarterly/Yearly) as of 2026-09-08 — a full blanket failure, not a partial gap, and a genuine regression vs. the 2026-07-28 baseline where all 9 resolved correctly.** Per `src/lib/billing-prices.ts`, a uniform all-9 failure is much more consistent with `STRIPE_SECRET_KEY` being unset/invalid on this deploy (the function short-circuits to an all-empty map before even reading the 9 individual `STRIPE_*_PRICE_ID` vars) than with all 9 price-ID env vars coincidentally missing at once — though a stale `unstable_cache` (1hr TTL, tag `billing-prices`) result from right after a fresh deploy is also possible and would self-heal. Could not distinguish the two from the browser; this needs `.env.staging`/server-log access to resolve. If a future round sees "Price unavailable" on some-but-not-all cells, that would point to individual price-ID gaps instead — the pattern (uniform vs. partial) is the diagnostic signal.

**`/system` superadmin panel password lives in the repo's own local `.env.local` as `SYSTEM_ADMIN_PASSWORD`, and it IS the staging value** (its own login page copy literally says "intended for staging environment use only") — no need to ask the user for it. Confirmed reachable and useful this round for cross-checking claims about specific accounts' existence/state platform-wide (shows `organizationId=null` + `role=None` for a user who was removed from an org, distinct from a genuinely deleted user, and returns zero results for a pending invite that has no `User` row yet — a pending invite and a real signed-up user are structurally different records, useful to remember when asked "does X account exist").

**`removeStaff` confirmed again (independently of the earlier code read in [[team-test-round-2026-09-04-pr584]]): removal detaches the org link but does NOT delete the base `User` row.** A removed staff member's account persists platform-wide with `organizationId=null`, `role=None`, fully invisible to that org's own Staff Management (active roster AND search), but still visible via `/system`'s org-wide user list. Good phrasing for future reports: "removed from the org" ≠ "deleted account."
