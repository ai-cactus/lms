**CONFIRMED FIX — seat count frees on staff removal (`de25ee93`), fully live-verified end-to-end, closing the bug found in the prior round.** Reached 10/10 cap → "Worker Limit Reached" modal correctly blocked a new invite → removed a throwaway staff member (deactivated, not the invite-revoke path) → gauge dropped to 9/10 immediately, survived a full reload → re-attempted "Add Staff" opened the normal dialog ("1 seat remaining") instead of the blocking modal → completed a real invite successfully. `countBillableStaff` (shared helper, filters `active: true`) now backs the Staff Management page's own count instead of a hand-rolled duplicate query that had drifted (no `active` filter) — same "second implementation of an existing rule" bug shape as other fixes this cycle.

**Important nuance surfaced while testing seat-count's "training record survives removal" sub-claim: `removeStaff` (`src/app/actions/staff.ts`) hard-DELETES in-flight enrollments on removal, and only retains terminal-status ones.** `ACTIVE_ENROLLMENT_STATUSES = ['enrolled','assigned','in_progress','lessons_complete']` are explicitly `deleteMany`'d ("so a re-invite yields a clean slate"); only `completed`/`attested`/`locked`/`failed`/`retry_requested` enrollments and their certificates survive, per the code's own comment. Live-confirmed: assigning a course to a throwaway worker then removing them dropped their "Total Courses Assigned" to 0 in BOTH their own (still-reachable, non-deleted) staff profile AND the Audit Reports → Staffs facility-scoped view. This is intentional/documented, not a regression — but it means "training record persists after removal" is only true for completed/compliance-relevant history, never for an in-progress assignment. Worth clarifying in any future story that references this behavior, since the plain-English framing ("removal deactivates rather than deletes") reads as unconditional but isn't.
