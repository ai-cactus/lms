**CONFIRMED FIX — course delete no longer shows "Minified React error #441".** `deleteCourse` (`src/app/actions/course.ts`) now scopes on `existing.creator?.organizationId === organizationId` (org ownership) instead of `createdByOrgUserId` (authorship) — a colleague-authored, org-owned course now deletes cleanly for any other manager. Live-proved the readable-refusal half too, via a genuine race: open the delete-confirm dialog for the same course in two browser sessions, confirm the real delete in one, then confirm the now-stale dialog in the other — server returns and UI shows **"Course not found."**, no crash, no #441. `buildRowActions` in `CoursesListClient.tsx` already omits the Delete item entirely for `isGlobalCatalog` rows client-side, so the server's matching "shared catalogue" refusal message is effectively unreachable through the UI (defense in depth, code-confirmed only).

**CONFIRMED FIX — `/worker/profile` reshelled onto the same left-sidebar-pill-tabs shell as `/dashboard/profile` (manager), AND the tabs are now genuinely keyboard-reachable.** Live keyboard-only proof technique that worked: `page.getByRole('link', {name:'Back'}).focus()` via `run-code`, then real `press Tab` × N while reading `document.activeElement.outerHTML` via `--raw eval "() => document.activeElement.outerHTML.slice(0,200)"` — confirms each pill is its own `<button role="tab">` Tab stop (not a roving-tabindex arrow-only pattern, and definitely not the old unreachable clickable-div). `press Enter` on the focused pill flips `aria-selected` and swaps the tabpanel — a real keyboard activation. Manager profile shares the exact same shell plus two extra pills ("My Organization", "My Facilities") it needs and the worker view correctly doesn't have.

**CRITICAL GAP — the "Duplicate" course row action does not exist anywhere in the shipped UI, on this exact staging commit (`9ea50d80`) or my local checkout.** `grep -rn "'Duplicate'" src/` (excluding tests) returns zero matches; the row-actions kebab on every owned course (video or reading, any role with `course.create`+`course.delete`, including HR) offers only Assign to staff / View Source Document / Rename / Delete. `duplicateCourse` (`src/app/actions/course.ts`) and `forkCourse` (`src/lib/course/fork-course.ts`) are both real and unit-tested in isolation, but nothing in the UI calls them. `CoursesListClient.test.tsx` still has test **titles** referencing Duplicate for HR (e.g. "hr sees Assign, View Source Document, Duplicate, Rename, Delete") but the test bodies don't actually assert its presence — a stale-title hygiene issue, not evidence the feature exists. **This blocks any live verification of the Draft→Published-on-assignment fix** (Story 6): that fix's whole precondition (a `status:'draft', reviewRequired:false` row with no assignment yet) is only reachable via `forkCourse`, and `forkCourse` is only reachable via the missing Duplicate button.

**Second, independent reason Story 6 can't be reached even with Duplicate wired up: the Create-Course wizard structurally cannot produce a persisted, unassigned Draft course.** `Step9AssignPublish.isAssignSelectionValid` gates the wizard's own "Publish Course" button — at least one role or individual must be selected before it enables. Nothing is written to `courses` until that click succeeds (`createFullCourse` is the only writer, called from `CourseWizard.handlePublish`). And when the quality gate passes (the normal case — 2/2 throwaway courses I generated this round passed it), `createFullCourse` sets `status: reviewRequired ? 'draft' : 'published'` — i.e. **published immediately at creation**, never touching Draft at all. The only way to land a genuine `draft` row is the non-deterministic `reviewRequired` quality-gate hold, which can't be forced on demand. Net: even a fully-wired Duplicate button gets you a draft row, but the wizard path for NEW courses can never produce one to duplicate FROM in the reviewRequired=false case — moot for this specific test since Duplicate targets an *existing* (already-published) course anyway, but worth remembering that "just make a new course and don't assign it" is NOT a way to reach Draft state live.

**New reusable technique — forcing a genuine "double delete" race without any tooling, to prove a refusal path is readable:** open the same row's delete-confirm dialog in two separate `playwright-cli` sessions (two logged-in accounts, or the same account in two tabs), confirm in one first, then confirm the now-stale dialog in the other. Cleanly reproduces `deleteCourse`'s "not found" branch live, no direct DB/API calls needed. Reusable any time a "was this refusal message user-friendly" criterion needs a forced-failure branch.

**Course-creation wizard mechanics confirmed (useful for future course-fixture builds):** 7 steps — category → module/doc upload (PHI checkbox mandatory) → course details (AI pre-fills title/description/objectives from the doc) → quiz config → generation (background job, poll `/dashboard/courses/queue`, `GENERATE V46_COURSE` → `Completed`) → content review → **Assign & Publish** (role/email picker is mandatory to enable Publish; a SECOND "Set Completion Deadline" dialog appears after the first "Assign Course" click and must ALSO be confirmed — easy to miss, looks like a no-op if you stop after the first click, but nothing is actually assigned/persisted-differently until the second dialog's own button fires). Generation state survives page nav via `localStorage['lms_pending_generation']`; revisiting `/dashboard/courses/create` offers "Resume Draft" which jumps straight to the review step. Confirmed working twice this round with `docs/local/Confidentiality Training - Series 1.pdf` (same known-good fixture as [[staging-course-generation-failing]]).

**NEW BUG — removing a staff member does not free the seat count.** At a Starter-plan 10/10 cap, removed a throwaway staff member via Staff Management row action → confirmed dialog → roster genuinely dropped back to 10 real rows (verified via `Showing 1 to 10 of 10 entries` + absence from a name search) — but the "10/10 seats used" banner persisted after a full reload, and a fresh "Add Staff" attempt hit a hard-blocking "Worker Limit Reached" modal despite the roster having room. Not root-caused (possibly the same class of stale/derived seat-count display documented for Billing/Staff Management headers in [[billing-subscription-patterns]] and [[staff-management-patterns]]), but this is the first time it's been shown to actually **block** a new invite rather than just misdisplay a number. This also blocked live-testing the exact longest Staff-Role display name this round (seat cap reached before a BHT-role fixture could be created) — the underlying truncate+title mechanism was still verified via code + a shorter long-name live case ("Facility Supervisor" truncating cleanly at 700px with a correct `title=` full-string attribute).
