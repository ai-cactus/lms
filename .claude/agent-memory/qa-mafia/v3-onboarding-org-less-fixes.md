Full live re-validation of 8 tester complaints (screenshots in `v3_errors/`) against the working-tree diff on branch `multi-facility`, both stories 13/9 criteria PASS, no regressions. Reports: `qa-reports/v3-fresh-owner-onboarding.md` and `qa-reports/v3-existing-user-reonboarding.md`.

**Settings' org-details tab is now called "Facility", not "Your Organization"** — a `multi-facility` model rename, not a bug. It shows a "Facility profile" panel (active facility name/type + an "Add Facility" affordance) instead of the old single-org card. Any story/screenshot referencing "Your Organization" tab should be read against this new tab.

**Root cause of the pervasive "No organization found" bug (Documents/Courses/Billing/Settings all showing it after a fresh signup): a Next.js Server Action redirect crash, not a data bug.** `authenticate()`'s `signIn(..., { redirectTo: '/dashboard' })` used to send a freshly-verified, org-less owner to `/dashboard`, but `/dashboard`'s own middleware/RSC redirect logic would then try to bounce it again — and a Server Action's `redirectTo` **must** name a route that renders, not one that itself redirects, or the client throws "An unexpected response was received from the server" (Next.js E394) instead of navigating. Fix: `authenticate()`/`authenticateWorker()` now compute the redirect target themselves (`/onboarding/step1` directly for a `none` membership resolution, never `/dashboard`), and `src/proxy.ts`'s org-less admin gate is explicitly skipped for `POST` requests carrying a `next-action` header (i.e. deferred until the ordinary GET/RSC navigation that follows an action, which is safe to gate normally). Also fixed: the onboarding-complete page's session cookie was stale (minted before the org existed) — `/onboarding/complete` now calls `useSession().update()` both on mount and again right before navigating to `/dashboard`, and `create-auth-instance.ts`'s JWT callback separately re-resolves membership for any org-less token whose owner has since joined an org (covers the "finished onboarding in another tab" case too). A `dashboard/courses` page.tsx band-aid also renders a friendly "Complete onboarding" empty state instead of crashing if `organizationId`/`organizationUserId` are ever still missing.

**Existing-user invite silently dropped in `completeOnboarding()`'s `queueInvite()` fixed by removing an `existingUser` early-return** — it used to skip creating the `invites` row entirely if `prisma.user.findUnique({where:{email}})` found a match, silently discarding any invite to an email that already existed anywhere in the system (a different org, or org-less). Multi-org membership is the model's whole point, so inviting an existing identity is legitimate and now always creates the invite row.

**Onboarding step1 (Org Details) fields (EIN, Street Address, Zip, City, State) are now all mandatory** both client-side (react-hook-form `required` rules + `Field required` prop, no more `(optional)` helper text) and server-side (`completeOnboarding()`'s `REQUIRED_STEP1_FIELDS` check, returns `code: 'MISSING_STEP1'` with a field-name list if any are blank) — verified the DB-level payoff too: `facilities.address/zip_code/city/state` are now always populated and `timezone` is correctly derived from the mandatory `state`, instead of a half-populated facility silently breaking downstream reminders/compliance reporting. The step1 "Skip for now" button was removed entirely (was `router.push('/dashboard')`, bypassing org creation altogether).

**Step3 (Services) checkbox-grid overflow was a Tailwind gutter-vs-container-width bug**, fixed by holding the 130px gutter back to `xl:` breakpoint (`sm:gap-x-12 xl:gap-x-[130px]`) plus `min-w-0`/`break-words` on each option label — confirmed genuinely fixed via a real DOM overflow scan (`scrollWidth > clientWidth` on every element) at both 1440x900 and 1280x720, not just a visual screenshot check.

**DB-harvest signup pattern that works reliably in local dev (no MailHog needed for a real end-to-end signup):** fill/submit `/signup` normally → lands on `/verify-email` → `SELECT token, role FROM verification_tokens WHERE identifier = '<email>' AND type = 'email_verification' ORDER BY expires DESC LIMIT 1` → `page.goto('/verify?token=<token>')` → click "Verify Email Address" → redirects to `/login?verified=true`. Matches `tests/e2e/signup-email-verification.spec.ts`'s own `getTokenFromDb` helper. A verified self-serve token always carries `role='owner'`.

See [[lms-v2-signup-onboarding-settings-flow]] for the pre-`multi-facility` route map (now partially superseded by the direct-to-onboarding login routing and the Facility tab rename above) and [[local-dev-env-access]]/[[local-dev-env-setup]] for the underlying DB/Redis/port setup this run used unchanged.
