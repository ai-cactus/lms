**Full report:** `qa-reports/vertex-retry-budget-ai-question-generation.md`. Verdict: PASS — 7/7 attempts (5× "Add new question → Generate with AI" + 2× "Regenerate Quiz") succeeded on staging (commit `6df70289`), latency range 2.8s-20.0s, zero 524s, zero generic errors, zero native dialogs. This directly follows up [[slide-editor-batch-2026-09-21]]'s HIGH finding (~2/3 attempts hit a Cloudflare 524 before this fix).

**Honest caveat, worth repeating in any future retest of this fix: the failure-path UX ("The AI service is taking longer than usual..." in-page message, no native dialog, working retry) was never actually observed** — no attempt this round got remotely close to the 45s budget (max was 20s), so the fix's *bounded-timeout* behavior itself is unverified by direct observation, only inferred from the code. If a future round wants to actually see this path, staging Vertex would need to be genuinely slow/rate-limited at that moment — can't be forced deterministically without fault injection (which this story explicitly wasn't asking for).

**Client-side JS polling to detect "has the question textarea been populated yet" is unreliable for this specific React form — use the network request log as ground truth instead.** A `page.evaluate`/`waitForFunction` script polling `document.querySelector('textarea[placeholder*="Enter your question here"]').value` twice reported "no resolution within 55s" for attempts that had actually succeeded seconds earlier (confirmed via a follow-up DOM snapshot showing the real generated question, and via the Server Action's own `duration`). Root cause not fully diagnosed (possibly transient execution-context churn during the RSC re-render), but the fix is straightforward: **track completion by polling `playwright-cli requests` for a new POST to the wizard route, then reading its `duration`/`status` via `playwright-cli request <id>`**, rather than trying to detect the DOM mutation from inside a single long-running `run-code` script. Cross-check with a plain `playwright-cli snapshot` afterward to confirm the UI actually reflects the new content.

**`playwright-cli response-body <id>` can return empty for a request that is genuinely 200/successful** (confirmed via DOM state) — a CLI decoding quirk on some RSC stream shapes, not a signal of a broken server response. Don't treat an empty response-body dump alone as evidence of a silent server failure; corroborate with the DOM.

**The "Add New Question" compact editor (course-creation wizard Step 6) does not display the AI's `explanation` field until the question is Saved into the main quiz list** — the raw Server Action response always includes `explanation`, but the pre-save edit form only shows Question Text + 4 Options + a correct-answer radio. Save once to actually see it rendered as "Correct: ...". Not a bug, just an editor-scope gap worth knowing before flagging "no explanation" prematurely.

**"Regenerate Quiz" is now confirmed to always run through an in-page shadcn `alertdialog`** ("Regenerate the whole quiz?" — explicit copy about losing manual edits/added questions), never a native `confirm()` — consistent with PR #657's alert/confirm replacement claim, and this is the only confirmation surface this generation flow has.
